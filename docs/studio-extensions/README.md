# D04 ADR 초안 — 확장 설치 위치와 관리 runtime 세대

> [Studio #32](https://github.com/handochan/aelix-studio/issues/32)의 D04 spike 결과다. 2026-11-17에
> native pin `e19ab55e`, ACP pin `16d6555b`, macOS arm64에서 확인했다. 같은 날 독립 리뷰를 받아 2차 실험을
> 하고 고쳤다(11절). 실험 명령과 출력은 [실험 기록](spike-evidence.md)에 있다.

상태: **Proposed (초안, 리뷰 1회 반영)** · 사용자 확정 전이다. 이 문서는 구현·병합·출시 승인이 아니다.
Windows, Linux, 서명된 설치 앱에서는 실행하지 않았다(10절). 판단의 정본은
[decisions.md](../studio-release-train/decisions.md)의 D04이고, 이 초안이 채택되면 그 표에 반영한다.

각 사실에는 근거를 붙였다. **[실행]** 은 번들 사본에서 돌려 본 것, **[소스]** 는 pin의 소스를 읽은 것,
**[추정]** 은 둘 다 아닌 것이다. 시험한 번들 사본은 main이 아니라 Studio #31 branch에서 준비한 것이다.
main과 다른 점과 그 영향은 3.2와 실험 기록에 적었다.

## 1. 결론

- 확장은 **사용자 영역의 얇은 venv 세대**에 설치한다. 세대에는 확장과, 번들에 없는 의존성만 들어간다.
  native와 ACP는 계속 번들에서 읽는다.
- 실행 형태를 둘로 나눈다(5.2).
  - **관리**(설치·업데이트·제거·목록): 세대의 venv interpreter로 native CLI를 실행한다. native CLI는 venv
    안에서만 설계대로 동작한다.
  - **대화**: 지금처럼 번들의 interpreter를 `-I -S`로 실행하고, launcher가 세대의 `site-packages`를 import
    경로 끝에 더한다. 확장은 `-e`로 명시한 것만 로드한다.
- 설치는 새 후보 세대에서 하고, 검증을 통과한 뒤에만 "현재 세대"를 가리키는 파일을 바꾼다. 검증은 대화와
  같은 형태로 native를 띄워 확장이 실제로 로드됐는지 묻는다(5.5). 실패하면 후보를 지운다.
- 확장을 하나도 설치하지 않은 사용자는 지금과 똑같이 번들만으로 실행한다.
- **만들 수 있는 것과 사용자에게 낼 수 있는 것은 다르다.**
  - 설치 helper(세대 만들기·설치·검증·전환·되돌리기)는 지금 native와 지금 ACP로 만들 수 있다. R8이 필요
    없다. 파일·이름·git·내부 index 설치, 업데이트, 제거, 오프라인 반입, 번들 교체 뒤 유지를 실행해 봤다.
  - 그것을 화면으로 내려면 먼저 정해지고 확인돼야 하는 것이 있다(9절): 설치한 확장을 켜고 끄는 단위
    (Studio #7과 함께), 대화창의 `/extension install`이 세대를 바꾸지 못한다는 OS별 확인, launcher 변경,
    Windows·Linux 확인.
- 이 설계가 보장하지 못하는 것을 구분해 적었다. 온라인 설치에서 "지정한 index에만 접속"은 보장하지
  못한다(5.10). 오프라인 반입의 "접속하지 않음"은 정적 검사와 설정으로 만들고, 증명은 출시 후보의 외부
  접속 감사에 맡긴다(5.9).
- overlay 디렉터리에 native CLI로 설치하는 방식은 채택하지 않는다. native가 출처 검사로 거부하고, 우회하면
  업그레이드와 제거에서 설치 기록이 깨졌다.

## 2. 지켜야 하는 것

이미 확정된 제약이다. 이 초안은 이를 바꾸지 않는다.

- native wheel은 수정하지 않는다(D01). 번들은 설치 뒤 바꾸지 않는다.
- host는 Aelix 전용 메시지를 그대로 넘기고, 전역 관리는 Studio helper가 한다(D05·D17).
- 새 Aelix 화면은 Aion 대화 저장소에 묶지 않는 독립 모듈이다(D20).
- R8이 보류인 동안 설치는 `aelix extension … --yes`를 실행하고 종료 코드로 판단한다.
- 켜기/끄기는 [Studio #7](https://github.com/handochan/aelix-studio/issues/7)이 맡는다.
- Studio를 업데이트해도 설치한 확장이 남는다(G16). 외부가 막힌 환경에서 wheel을 반입할 수 있다(G12).
- 사용자의 시스템 CLI를 임의로 업데이트하지 않는다(D04). 사용자가 동의한 설치까지 금지한 것은 아니다.
- 첫 Beta 필수 항목은 줄이지 않는다. 줄이려면 사용자 승인이 필요하다(decisions.md 사용자 결정 기록).

## 3. 확인한 사실

### 3.1 native 설치가 하는 일

pin `e19ab55e` 기준이다. aelix-ai `origin/main`(`bf507d59`)의 `extension_install.py`는 주석 한 줄만 다르다. **[소스]**

| 설치 도구   | pip을 import할 수 있으면 pip. 아니면 `PATH`의 `uv`(절대 경로일 때만). 둘 다 없으면 설치하지 않고 종료 코드 2                                                                                                                                                 | 소스·실행          |
| 실행 방식   | 자식 프로세스 `sys.executable -P -m pip install <대상>`. 부모의 환경 변수와 pip 설정을 물려받는다. 의존성은 pip이 푼다                                                                                                                                       | 소스·실행          |
| 설치 기록   | `<agent dir>/settings.json`의 `extensionSources`와 `<agent dir>/extension_pins.json`에 쓴다. **환경별이 아니라 agent dir별**이다. 이름 없는 `extension update`는 기록된 것을 전부 지금 환경에 다시 설치한다                                                  | 소스·실행          |
| 종료 코드   | 0 설치됨, 1 설치 도구가 실패함, 2 설치 도구를 실행하지 않음(인자 오류·거부·설치 도구 없음), 3 설치됐지만 manifest가 묶이지 않음. `remove`만 pip의 코드를 그대로 돌려준다                                                                                     | 소스. 0·1·2는 실행 |
| 시작 시     | 로더가 `sys.path`의 `*.dist-info`에서 entry point 그룹 `aelix.extensions`를 찾는다. 배포판이 interpreter의 설치 디렉터리(`purelib`·`platlib`·`site.getsitepackages()`·user site) 밖에 있으면 **거부한다**. `--trust-extension-path <배포판>`만 예외를 만든다 | 소스·실행          |
| 지연 활성화 | manifest의 활성화 조건이 `on_command`뿐인 pack은 시작할 때 **import하지 않고** 목록에만 넣는다. 그 명령을 처음 쓸 때 import와 `setup()`을 한다                                                                                                               | 소스·실행          |
| 목록        | `extension list`와 control-v1 `extensions/list`는 설치 장부(entry point)를 읽는다. `extensions/list`는 이름·배포판·버전·entry만 준다. 로드 여부나 오류는 없다                                                                                                | 소스·실행          |

| 요구 사항   | pip(또는 uv), 쓸 수 있는 환경. git 설치는 `git`. wheel이 아닌 소스(git·sdist)는 빌드 도구를 index에서 받고 빌드 코드를 실행한다                                                                                                                              | 실행               |

### 3.3 ACP가 하는 일

Studio 대화는 ACP 어댑터가 띄운 native worker에서 돈다. 이 부분은 결정 문서와 Issue에 적혀 있지 않았다.

- 어댑터는 worker를 `--mode rpc --offline --no-extensions`로 시작하고, 명시한 것만 `-e`로 넘긴다
  (Analytics 확장, `--extension` 인자, 세션에서 켠 것, 승인 브리지). **[소스]**
- 그래서 대화에서는 pip으로 설치한 확장도, 사용자의 전역 디렉터리 확장도 로드되지 않는다. 세대에 설치한
  확장은 `/extension list`에 나오지만 그 확장의 `/hello`는 "Unknown slash command"였다. **[실행]**
- 어댑터 인자 `--extension`으로 넘기면 로드된다. 넘기는 형태에 따라 결과가 다르다. **[실행]**

  | `--extension`에 주는 것                          | 결과                                                                                                                                                                     |
  | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | 모듈 참조(entry point 값, `aelix_starter:setup`) | 시작할 때 import하고 `setup()`을 실행한다. **manifest 없이** 로드된다. 코드로 등록하는 명령·도구는 되고, manifest로 선언한 MCP 서버·테마·hook과 capability 검사는 빠진다 |
  | 세대 안의 패키지 디렉터리                        | 위와 같다. 그 디렉터리의 `__init__.py`를 파일로 로드한다                                                                                                                 |
  | pack마다 링크 하나를 둔 디렉터리                 | **manifest까지** 로드된다(확장 이름이 plugin id로 나오고 지연 활성화가 적용된다). 디렉터리 안의 하위 디렉터리를 manifest pack으로 읽는 native 동작을 쓴 것이다           |

- `--extension`으로 넘긴 확장은 어댑터의 launch 설정 소유가 된다. 세션에서 `/extension disable`을 하면
  `-32004 extension_owned_by_launch`로 거부한다. launch에 넣지 않은 확장은 세션이 `/extension enable`·
  `disable`로 켜고 끈다(승인 요청 뒤 worker 재시작). **[실행]**
- 어댑터에는 대화용 `/extension install|update|remove|list|verify` 등이 이미 있다. 승인 요청 뒤
  `aelix extension …`을 실행한다. 실행 파일은 `--extension-manager`가 있으면 그것, 없으면 worker의
  interpreter다. 쓰기 동작은 실행 파일의 실제 경로에 `.app/Contents/`가 들어 있을 때만 막는다. **[소스]**
- 대화의 `/extension install <wheel>`을 승인했을 때의 결과는 worker를 무엇으로 띄웠는지에 달려 있다. **[실행]**

  | worker                                                                  | 결과                                                                                                                                                                |
  | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 세대의 venv interpreter                                                 | **현재 세대가 그 자리에서 0.1.0에서 0.2.0으로 바뀌었다.** 후보·검증·전환을 거치지 않는다                                                                            |
  | 번들 interpreter(`-I -S`) + 세대 `site-packages` 추가                   | 실패한다("Aelix extension manager failed"). pip이 번들 Python의 `EXTERNALLY-MANAGED`를 보고 거부한다. 세대는 그대로다. `uv`가 `PATH`에 있어도 같다. `remove`도 같다 |
  | 세대의 venv interpreter + `--extension-manager <번들>/native/bin/aelix` | 실패한다. 세대는 그대로다                                                                                                                                           |

### 3.4 pip이 하는 접속

| 설정                                                               | 관찰                                                                                                              | 근거 |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ---- |
| native `--offline`만                                               | 빠진 의존성을 PyPI에서 받았다                                                                                     | 실행 |
| `--offline` + `PIP_NO_INDEX=1` + 로컬 `PIP_FIND_LINKS`             | wheel이 직접 URL 의존성(`이름 @ http://…`)을 선언하면 그 URL에서 받았다                                           | 실행 |
| 위에 사용자 pip 설정 파일이 있을 때                                | 설정의 `find-links = http://…`에 접속했다. `PIP_CONFIG_FILE`을 빈 장치로 주면 접속하지 않았다                     | 실행 |
| 소스 묶음(sdist)을 줄 때                                           | `PIP_ONLY_BINARY=:all:`을 줘도 빌드 자식이 시작됐다. index가 없어 빌드 도구를 받지 못해 실패했을 뿐이다           | 실행 |
| 위 설정에 죽은 proxy(`HTTP_PROXY=http://127.0.0.1:9` 등)를 더할 때 | 직접 URL 내려받기가 "proxy-connection-failed"로 막혔다. 정상 반입에는 영향이 없었다                               | 실행 |
| 접속과 무관한 소켓 호출                                            | `urllib3`(번들의 것과 pip에 든 것)가 import될 때 `::1`의 포트 0에 bind해 IPv6 지원을 확인한다. 연결도 전송도 없다 | 실행 |

## 4. 검토한 선택지

| 방식                   | 설명                                                                                       | 실험 결과                                                                                                                                                                                                                                                                                                                                                                  | 판단                              |
| ---------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| 얇은 venv 세대         | 사용자 영역에 번들 Python으로 venv를 만든다. native는 번들에서 읽고 확장만 venv에 설치한다 | native CLI가 설계된 대로 동작했다(pip, 설치 디렉터리 인정, 제거, 목록). 3.1의 명령 전부와 5절의 절차를 실행했다. 번들은 끝까지 그대로였다                                                                                                                                                                                                                                  | **권장**                          |
| overlay 디렉터리       | 번들 Python을 그대로 쓰고 사용자 영역 디렉터리 하나에 native CLI로 설치한다                | `sys.path`에만 더하면 native가 "REFUSED (untrusted sys.path provenance)"로 거부했다. `PYTHONUSERBASE`로 user site인 것처럼 알리면 통과했다. native CLI로 설치하려면 pip을 환경 변수로 돌려야 했다. 업그레이드하니 pip이 패키지 디렉터리를 바꾸지 않았고 0.1.0과 0.2.0 기록이 함께 남았는데 종료 코드는 0이었다. 제거한 뒤에는 기록만 남은 "manifest not bound" 항목이 됐다 | 제외. native 지원이 생기면 재검토 |
| 전체 복제 환경         | 사용자 영역에 native wheel까지 넣은 독립 환경을 만들고 거기서 실행한다                     | 실행하지 않았다. 번들에는 wheel 파일이 없고 설치된 트리만 있다. 실행 코드가 서명·목록 밖의 사용자 쓰기 영역으로 옮겨지고, pip이 native 의존성을 바꿀 수 있다                                                                                                                                                                                                               | 제외                              |
| 사용자 CLI 환경에 설치 | Studio가 사용자의 터미널 `aelix`가 쓰는 환경에 직접 설치한다                               | 실행하지 않았다. Studio runtime은 그 환경의 패키지를 볼 수 없다(6절). Studio 대화용 설치를 대신할 수는 없고, 범위에 둘지는 사용자 결정이다(8.2의 1·2)                                                                                                                                                                                                                      | Studio 대화용으로는 제외          |

overlay가 통과한 `PYTHONUSERBASE` 경로는 `-I`가 그 변수를 무시한다는 문서와 달리 `site.getusersitepackages()`가
환경 변수를 직접 읽기 때문에 생긴다. Python이 고치면 사라질 동작이라 설계 근거로 쓰지 않는다. **[실행·추정]**

권장안의 대화 실행(5.2)은 번들 interpreter에 세대 디렉터리를 더하므로 import 경로만 보면 overlay와 같다.
다른 점은 설치와 장부 관리를 venv 안에서 native CLI가 하고, 대화에서는 `-e`로만 로드해 출처 검사를 거치지
않는다는 것이다.

## 5. 권장 설계

### 5.1 위치와 구성

Studio 사용자 데이터 디렉터리 아래에 둔다. 앱 번들, 사용자의 CLI 환경, CLI와 공유하는 `~/.aelix` 어디에도
쓰지 않는다. 정확한 디렉터리 이름은 구현에서 정한다.

```text
<Studio 사용자 데이터>/aelix-runtime/
  lock                         변경 작업의 프로세스 간 잠금
  current.json                 현재 세대, 이전 세대, revision, 묶인 번들 정보 (직전 사본도 둔다)
  constraints-<lock>.txt       번들에 설치된 배포판과 버전(번들에서 계산)
  artifacts/<묶음>/            파일로 반입한 wheel과 그 sha256 목록
  leases/                      실행 중인 launcher가 쓰는 세대 표시
  generations/<id>/
    venv/                      번들 Python으로 만든 venv. 확장과 추가 의존성만 들어간다
    agent/                     native 설치 기록과 pin (세대와 함께 복제·폐기)
    generation.json            배포판별 이름·버전·RECORD 해시, 확장 entry, 묶인 번들. 이 파일이 있어야 완성된 세대다
```

- 세대는 번들의 경로, `target`, Python minor 버전, `dependencyLockSha256`, native commit에 묶는다(번들
  `manifest.json`에서 읽는다). D04의 "bundled source/ABI/lock에 연결"이 이것이다.
- 세대 하나는 약 12MB였다. 거의 전부 세대마다 들어가는 pip이다. **[실행]**

### 5.2 두 가지 실행 형태

|                         | 관리                                                     | 대화                                                                       |
| ----------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| 쓰는 곳                 | helper의 설치·업데이트·제거·목록·`extension verify`      | ACP가 띄우는 worker, 전환 전 로드 검증                                     |
| interpreter             | `<세대>/venv/bin/python`                                 | 번들의 Python (지금과 같다)                                                |
| 인자                    | `-I -B -X utf8 <번들>/launch.py native …`                | `-I -S -B -X utf8 <번들>/launch.py`에 세대 `site-packages` 경로를 넘긴다   |
| `site` 모듈             | 켜짐. Python 3.12는 venv 인식을 `site`가 한다            | 꺼짐 (지금과 같다)                                                         |
| `sys.path`              | `native-site`, 표준 라이브러리, 세대 `site-packages`     | `native-site`, 표준 라이브러리, 세대 `site-packages`(launcher가 끝에 추가) |
| 세대의 코드가 실행될 때 | 시작 코드가 없다는 정적 검사(5.3)를 통과한 세대만 띄운다 | `-e`로 넘긴 확장만. `.pth`와 `sitecustomize`는 실행되지 않는다             |
| 확장                    | 로드하지 않는다. 설치 장부(entry point)를 읽고 쓴다      | `--no-extensions`와 확장마다 `-e`로 로드한다                               |

대화를 번들 interpreter로 두는 이유다. 모두 실행해 확인했다. **[실행]**

- 세대에 `sitecustomize.py`가 있으면(`.pth`는 하나도 없이) venv interpreter에서는 launcher보다 먼저 실행돼
  세대의 `packaging 23.2`가 쓰였다. `sys.path` 맨 앞이 `native-site`인데도 그랬다. 번들 interpreter에 `-S`로
  세대를 더한 실행에서는 번들의 26.3이 쓰였고 `sitecustomize`도 `.pth`의 코드도 실행되지 않았다.
- 대화의 `/extension install`·`remove`가 세대를 바꾸지 못했다(3.3).
- 대화마다 사용자 영역의 실행 파일을 띄우지 않는다. 사용자 영역의 Python은 설치할 때만 쓴다.
- interpreter와 `-I -S -B` 인자가 지금 번들과 같다. 확장을 `--extension`으로 넘기지 않으면 세대의 코드는
  아무것도 실행되지 않는다.
- 수정하지 않은 ACP 어댑터로 확장의 명령과, 세대에만 있는 의존성(`tabulate`)을 쓰는 명령이 실행됐다.

이 형태의 한계다.

- 확장이 `sys.executable`로 자식 Python을 띄우면 그 자식은 세대를 보지 못한다("No module named"). venv
  interpreter로 띄운 worker에서는 보였다. 지금 번들도 같은 제약이 있다(자식이 번들 패키지를 import하지
  못한다). **[실행]**
- 대화의 `/extension list`는 로드된 확장을 "REFUSED (untrusted sys.path provenance)"로 적는다. 장부를 읽는
  명령이 출처 검사를 적용하기 때문이다. 문구를 고치려면 ACP 변경이 필요하다(7.3). **[실행]**
- entry point 경로로는 로드할 수 없다(출처 검사). ACP가 `--no-extensions`를 쓰는 동안은 해당이 없다.

launcher 변경이 필요하다. `launch.py`는 세대 `site-packages` 경로를 인자로 받아 `sys.path` 끝에 더하고,
`launch.cjs`는 시작할 때 `current.json`을 읽어 그 경로와 `--extension` 인자를 만든다. host 설정에 저장된
실행 인자에는 세대 경로를 넣지 않는다(D17). 번들 구성 변경이라 다른 작업과 직렬로 한다.
**[실행: 같은 일을 하는 시험용 launcher로 확인했다. 번들의 launcher를 고친 것은 아니다]**

### 5.3 시작 코드와 번들 이름 정책

정책은 "세대 안의 코드는 `-e`로 넘겼을 때만 실행된다"이다. 대화 실행은 `-S`로 이를 지킨다. 관리 실행은
`site`를 켜야 하므로, **세대의 interpreter를 띄우기 전에** 파일만 읽는 검사를 한다.

- 세대 `site-packages` 맨 위에 `.pth` 파일, `sitecustomize`, `usercustomize`가 없다.
- `pyvenv.cfg`가 Studio가 쓴 내용과 같다.
- 번들과 같은 이름의 배포판이 없다. 번들과 같은 최상위 모듈·패키지 이름이 없다.

검사는 후보를 만든 직후(물려받은 내용)와 설치 도구가 끝난 직후에 한다. 설치 뒤 검사가 실패하면 후보의
interpreter를 다시 띄우지 않고 지운다. `sitecustomize.py`를 싣는 wheel, `.pth`를 싣는 wheel, `packaging/`을
싣는 wheel이 모두 설치 뒤 검사에서 걸려 전환되지 않았다. **[실행]**

최상위 이름 검사는 번들과 namespace를 공유하는 패키지(예: `google.*`)도 거부한다. 예외를 둘지는 구현에서
정한다. **[추정]**

### 5.4 설치·업데이트·제거 절차

1. 파일 반입이면 정적 검사(5.9)를 하고, 통과한 wheel 묶음을 `artifacts/`에 복사한다. 설치는 그 사본으로 한다.
2. 잠금을 잡는다. 완성되지 않은 후보를 지우고 현재 포인터와 revision을 읽는다(5.6).
3. 후보를 만든다. 번들 Python으로 새 venv를 만들고(오프라인, 복사까지 약 2초), 부모 세대의 `RECORD`에 적힌
   파일을 전부 복사한다. console script와 `site-packages` 밖의 data 파일이 포함된다. 스크립트 첫 줄의
   interpreter 경로를 후보의 것으로 고친다. `agent/`를 복사한다.
4. 정적 검사(5.3)를 한다.
5. 후보에서 native CLI를 관리 형태로 실행한다: `--offline`(반입일 때) `extension install|update|remove <대상> --yes`.
6. 종료 코드가 0이 아니면 후보를 지운다.
7. 정적 검사를 다시 한다. 실패하면 후보를 지운다.
8. 검증한다(5.5). 하나라도 실패하면 후보를 지운다.
9. `generation.json`을 쓰고, revision이 2번에서 읽은 값과 같은지 확인한 뒤 `current.json`을 임시 파일에
   쓰고 rename으로 바꾼다.

1차 실험의 후보 복제는 `site-packages`만 복사했다. 그 방식으로는 다음 설치 뒤에 console script와 data
파일이 사라졌다. `RECORD` 기준 복사로 바꾸니 남았고 스크립트가 새 세대의 interpreter로 실행됐다. **[실행]**

native CLI에 넘기는 환경은 Studio가 새로 만든다. 사용자 환경의 `PYTHON*`, `PIP_*`, `UV_*`, `VIRTUAL_ENV`,
proxy 변수는 넘기지 않는다. 부모(`-I`)는 `PYTHON*`을 무시하고 pip 자식만 읽는다. **[실행]**

| 환경 변수                             | 이유                                                                                                                                   |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `AELIX_CODING_AGENT_DIR=<세대>/agent` | native가 설치 기록을 CLI와 공유하는 `~/.aelix/agent/settings.json`에 쓰지 않게 한다. 버린 후보의 기록도 함께 사라진다                  |
| `PYTHONPATH=<번들>/native-site`       | pip이 번들에 이미 있는 패키지를 설치된 것으로 본다. 없으면 pip은 번들에 무엇이 있는지 모른다                                           |
| `PIP_CONSTRAINT=<constraints URL>`    | 번들과 다른 버전을 요구하는 확장을 설치 단계에서 실패시킨다. 없으면 pip이 다른 버전을 세대에 깔고, 실행 때는 번들 버전이 조용히 이긴다 |
| `PIP_CONFIG_FILE=<빈 장치>`           | 사용자의 pip 설정이 설치 위치와 접속 대상을 바꾸지 못하게 한다(3.1·3.4). 8.2의 8번에 따라 달라질 수 있다                               |
| `PYTHONDONTWRITEBYTECODE=1`           | 번들 표준 라이브러리에 `.pyc`가 생기지 않게 한다(3.2). main의 launcher에서는 Studio가 주지 않으면 번들이 바뀐다                        |
| `PIP_DISABLE_PIP_VERSION_CHECK=1`     | pip이 스스로 PyPI에 버전을 묻지 않게 한다                                                                                              |
| `PIP_NO_INPUT=1`                      | pip이 입력을 기다리며 멈추지 않게 한다                                                                                                 |
| 오프라인 반입일 때                    | `PIP_NO_INDEX=1`, `PIP_FIND_LINKS=<보관소 URL>`, 죽은 proxy(5.9)                                                                       |
| `PIP_INDEX_URL`                       | `update`에는 `--index-url`이 없어 이 변수로 내부 index를 준다                                                                          |

`PIP_CONSTRAINT`와 `PIP_FIND_LINKS`는 공백으로 값을 나눈다. "Application Support"처럼 공백이 있는 경로는
깨졌고, `file://` URL로 주니 공백과 한글 경로에서 동작했다. **[실행]**

### 5.5 전환 전 검증

| 검사                                                                                                                                                              | 잡는 것                                                    | 실행한 실패 예                                                                                                             |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 정적 검사(5.3)                                                                                                                                                    | 시작 코드, 번들과 겹치는 배포판·모듈                       | `sitecustomize.py`, `.pth`, `packaging/`을 싣는 wheel. constraints 없이 설치해 `packaging 23.2`가 깔린 경우                |
| native 종료 코드 0                                                                                                                                                | 설치 도구 실패                                             | 번들과 충돌하는 의존성(`packaging<24`, 번들 26.3): pip `ResolutionImpossible`, 종료 코드 1                                 |
| **로드 검사.** 대화 형태로 native를 띄운다: `--mode rpc --offline --no-session --no-extensions`와 확장마다 `-e <모듈 참조>`. control-v1 `resources/list`를 읽는다 | 모든 확장이 `extensions`에 있고 `extensionErrors`가 비었다 | import가 깨진 pack, `setup()`이 예외를 내는 pack. 둘 다 지연 활성화 pack이었고 native 설치는 0, `status`는 오류 없음이었다 |
| manifest까지 로드하는 형태를 쓰면(8.2의 3번) 그 인자로 한 번 더                                                                                                   | manifest 오류, capability 거부                             | 실행한 실패 예 없음                                                                                                        |
| `aelix extension verify`                                                                                                                                          | manifest 결합 상태. 화면에 보일 상태로 기록한다            | —                                                                                                                          |

- 로드 검사를 `-e <모듈 참조>`로 하는 이유: 이 경로는 지연 활성화가 없어 import와 `setup()`이 그 자리에서
  실행된다. 깨진 pack 두 종류(import 실패, `setup()` 실패)에서 `status --json`은 둘 다 통과했고, entry
  point를 직접 import하는 검사는 `setup()` 실패를 놓쳤고, 이 검사만 둘 다 잡았다. **[실행]**
- 로드 검사에는 후보의 `agent/`를 agent dir로 준다. 대화와 같은 agent dir을 주면 native가
  `~/.aelix/agent/auth.json`을 만든다. **[실행]**
- 검증은 확장의 `setup()`을 실행한다. 사용자가 설치를 승인한 코드다. 확장의 명령을 실제로 실행해 보지는
  않는다. 명령 안에서 나는 오류는 잡지 못한다.
- entry point 경로에서 지연 활성화 pack을 명령 실행 없이 확인하는 방법은 native에 없다(7.2). 대화가 그
  경로를 쓰지 않는 동안은 필요하지 않다.

### 5.6 동시 실행, 중단, 정리

- **잠금.** 설치·업데이트·제거·되돌리기·번들 교체 처리·정리는 `lock` 파일의 OS 잠금을 잡고 한다. 두
  프로세스가 동시에 설치를 시작하니 둘째가 8초 기다린 뒤 첫째의 결과 위에 설치했고 두 확장이 모두 남았다.
  **[실행: macOS의 `flock`. Windows의 잠금은 확인하지 않았다]**
- **revision.** 포인터에 revision을 둔다. 전환 직전에 다시 읽어 후보를 만들 때의 값과 다르면 전환하지
  않는다. 잠금이 기대대로 동작하지 않는 파일 시스템을 위한 이중 확인이다. **[실행: 값이 올라가는 것만]**
- **중단된 후보.** `generation.json`이 없는 세대 디렉터리는 완성되지 않은 후보다. 다음 변경 작업이 잠금을
  잡은 뒤 지운다. **[실행]**
- **포인터.** 임시 파일에 쓰고 디스크에 내린 뒤 rename한다. 직전 포인터의 사본을 남긴다. 포인터를 읽을 수
  없거나 가리키는 세대가 완성되지 않았으면 직전 사본을 쓰고, 그것도 안 되면 번들만으로 시작한다. 잘린
  포인터로 시험하니 직전 사본으로 시작했다. 마지막 전환 한 번이 빠진 상태가 된다. **[실행]**
- **실행 중인 세대.** launcher는 시작할 때 고른 세대에 lease 파일을 만들고 프로세스가 끝날 때까지 잠금을
  잡는다. 정리는 현재·이전 세대와 잠금이 살아 있는 세대를 지우지 않는다. lease를 잡은 프로세스가 있는
  동안 그 세대는 남았고, 끝난 뒤 정리에서 지워졌다. **[실행]**
- **반입 보관소.** 어느 세대의 기록도 가리키지 않는 묶음은 정리에서 지운다. **[추정: 구현하지 않았다]**
- 실행 중인 어댑터는 시작할 때의 세대를 계속 쓴다. 새 세대는 새 세션부터 적용한다.

### 5.7 되돌리기

- 실패한 작업은 전환 자체를 하지 않으므로 되돌릴 것이 없다. **[실행]**
- 사용자가 직전 상태로 되돌릴 때, 이전 세대가 지금 번들에 묶여 있으면 포인터만 바꾼다. 다른 번들에 묶여
  있으면 5.8과 같이 그 내용을 새 후보로 옮겨 검증한 뒤 전환한다. **[실행]**
- 되돌리기는 직전 한 단계다(8.2의 13번).

### 5.8 Studio 업데이트 (G16)

세대는 앱 밖에 있어 번들을 교체해도 파일은 남는다. launcher는 시작할 때 세대가 묶인 번들 정보와 지금
번들을 비교한다. 다르면 그 세대를 쓰지 않고 번들만으로 시작하며, helper가 아래를 한다. **기존 세대는
고치지 않는다.** 1차 실험은 현재 세대의 링크를 먼저 고친 뒤 검증했는데, 검증이 실패하면 고친 상태로 남는
결함이 있었다.

| 새 번들                                 | 처리                                                                                                          | 확인                                                                                                             |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 같은 Python minor                       | 새 번들의 Python으로 후보 venv를 만들고 현재 세대의 내용을 복사한다. 5.3–5.5를 거쳐 전환한다                  | 실행. 옛 번들을 지운 뒤에도 내용을 옮겨 전환했다. 옛 세대의 링크는 지워진 번들을 가리킨 채 그대로였다            |
| 위 검증이 실패(새 lock과 겹치거나 빠짐) | 빈 후보에 설치 기록을 순서대로 다시 설치하고 검증·전환한다                                                    | 실행(모의). 번들이 `tabulate`를 싣게 된 경우와 빼게 된 경우. 보관소의 wheel로 네트워크를 전부 막고 다시 만들었다 |
| Python minor가 다르다                   | 설치된 파일을 재사용할 수 없다. 설치 기록으로 다시 만든다. 컴파일된 모듈이 든 wheel은 새 버전용이 있어야 한다 | 1차에서 감지만 실행. 3.13 번들이 없어 다시 만들기는 실행하지 않았다                                              |

다시 만들 때 쓸 수 있는 것을 정의한다.

| 설치 방식   | 남는 것                                                                      | 다시 만들기                                                       |
| ----------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 파일 반입   | 반입한 wheel과 같은 폴더의 의존 wheel 전부의 사본, 파일별 sha256             | 오프라인으로 가능. 같은 바이트를 다시 설치한다 **[실행]**         |
| 이름(index) | 이름, 설치된 버전, 배포판의 `RECORD` 해시, index 주소. **wheel 사본은 없다** | index에 다시 접속해야 한다. 같은 버전을 지정할 수 있다 **[추정]** |
| git         | 주소와 설치된 commit                                                         | git 주소와 빌드 도구 index에 다시 접속해야 한다 **[추정]**        |

- 이름·git 설치도 wheel 사본을 남기려면 Studio가 `pip download`를 직접 실행해 받은 뒤 그 사본으로 설치해야
  한다. `aelix extension`만 쓴다는 규칙의 예외라 사용자 결정으로 둔다(8.2의 12번).
- 다시 만들 수 없을 때의 동작은 G16에 닿는다. 사용자 결정으로 둔다(8.2의 11번).
- 이전 세대는 옛 번들에 묶여 있어 그대로는 실행할 수 없다. 되돌릴 때 내용을 옮긴다(5.7).
- CLI와 공유하는 `~/.aelix`는 이 과정에서 쓰지 않는다. G16의 "공유 원본은 보존"과 맞는다.

### 5.9 오프라인 wheel 반입 (G12)

native의 `--offline`과 pip 환경 변수만으로는 접속을 막지 못한다(3.4). 다음을 함께 쓴다.

1. **설치 도구를 실행하기 전의 정적 검사.** 반입 묶음의 파일을 읽기만 한다.
   - wheel만 받는다. 소스 묶음은 빌드 코드를 실행하고 빌드 도구를 받으려 한다.
   - 어느 wheel이든 직접 참조 의존성(`이름 @ URL`)이 있으면 거부한다.
2. 통과한 묶음을 보관소에 복사하고 그 사본으로 설치한다. `--offline`, `PIP_NO_INDEX=1`,
   `PIP_FIND_LINKS=<보관소>`, pip 설정 파일 무시.
3. 보조 장치로 죽은 proxy를 설치 도구 환경에 준다. 정적 검사를 빠져나간 HTTP 요청이 있어도 나가지 못한다.

각 실험이 무엇의 증거인지 구분한다.

| 실험                                                                                                   | 증거가 되는 것                                                                                                               | 증거가 되지 않는 것                                        |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| macOS sandbox로 네트워크를 전부 막고 반입(의존성 없음, 의존성이 폴더에 있음, 번들 교체 뒤 다시 만들기) | 막힌 환경에서 절차가 끝까지 성공한다                                                                                         | 접속을 시도하지 않는다는 것                                |
| 직접 URL 의존성이 있는 wheel                                                                           | 정적 검사가 설치 도구를 실행하기 전에 거부한다. 검사 없이 같은 설정이면 접속을 시도한다                                      | —                                                          |
| Python 소켓 호출 추적(audit hook): native 부모, pip 자식, `extension verify`, 로드 검사                | 이 실행에서 연결·이름 조회·전송 호출이 없었다. `urllib3`의 `::1` bind 확인만 있었다. 직접 URL wheel에서는 연결 시도가 잡혔다 | 다른 OS, 다른 패키지, Python 밖의 코드(컴파일된 모듈, git) |
| sandbox가 system log에 남긴 거부 기록                                                                  | curl과 pip의 연결 시도가 기록된다                                                                                            | 횟수. `urllib3`의 bind 시도 일부가 기록되지 않았다         |

제품 보장("반입 중 외부 접속 없음")의 증명은 출시 후보의 외부 접속 감사(Studio #15)에 "오프라인 반입"
시나리오를 넣어서 한다. 아직 실행하지 않았다. `urllib3`의 loopback bind는 그 감사에서 따로 분류해야 할 수
있다. **[추정]**

의존성이 없는데 폴더에도 없는 wheel은 약 2초 만에 종료 코드 1로 끝났고 현재 세대는 그대로였다. venv
만들기는 번들 Python에 든 pip wheel을 써서 오프라인이다. **[실행]**

### 5.11 실행 주체와 화면 모듈 인터페이스

- 설치는 **Studio helper 서비스**가 한다. Provider 설정이 쓰는 `NativeAuthService`
  (`packages/web-host/src/studio-auth/`)와 같은 자리, 같은 방식이다. 데스크톱은 IPC로, WebUI는 로그인한
  사용자의 요청으로 부른다. 세대 interpreter를 argv로 직접 실행하고 shell을 쓰지 않는다.
- host와 ACP를 거치지 않는다. 실행 중인 worker를 건드리지 않는다(D05·D17). 변경은 5.6의 잠금으로 한 번에
  하나만 한다.
- 화면 모듈(D20)은 아래 요청만 안다. pip, venv, 세대 경로는 모른다.

| 요청                                                      | 응답                                                                                                                                                             |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list`                                                    | 현재·이전 세대 ID, 적용 시점(새 세션), 확장별 이름·배포판·버전·출처·상태(준비됨 / manifest 미결합 / 다시 설치 필요), 터미널 CLI 쪽 항목(6절, 8.2의 1·2번에 따라) |

| `update` / `remove` (이름)                                | 작업 ID                                                                                                                                                          |
| `rollback`                                                | 바뀐 현재 세대                                                                                                                                                   |
| `poll` / `cancel` (작업 ID)                               | 단계(검사 / 준비 / 설치 / 검증 / 전환됨 / 실패 / 취소됨), 실패 코드, 설치 도구 출력의 끝부분(길이 제한)                                                          |

실패 코드는 지금 정보로 낼 수 있는 것만 둔다: 반입 거부(wheel 아님, 직접 URL 의존성), 설치 도구 실패, 실행

| entry point 확장만 켜는 실행 인자(`--no-extensions`는 디렉터리 확장과 함께 끈다)                              | `-e`로 하나씩 넘긴다                                       | 소스 |
| 제거할 때 남는 의존성 정리                                                                                    | 없음. `extension remove tabulate`는 종료 코드 2였다        | 실행 |
| 설치 기록과 pin을 환경별로 두기                                                                               | 세대별 agent dir                                           | 실행 |
| `extensions/list`에 manifest 결합·로드·오류·출처 상태                                                         | `extension verify`와 `resources/list`를 따로 실행          | 소스 |
| 추가 확장 디렉터리를 설치 위치로 인정하는 방법                                                                | 없음. overlay 설치를 제외한 이유다                         | 실행 |

R8과 별개로 버그로 알릴 것이 두 가지다.

- `aelix --offline extension install <경로>`가 빠진 의존성을 공개 index에서 받는다(3.4). **[실행]**
- `extension remove`만 pip의 종료 코드를 그대로 돌려준다. 다른 동작의 0/1/2/3 구분과 다르다. **[소스]**

### 7.3 ACP에 필요한 것

Studio 쪽에서 우회하지 않고 ACP 변경으로 요청한다.

- **대화의 `/extension install|update|remove`.** 권장한 대화 실행 형태에서는 실패해서 세대를 바꾸지
  못한다(3.3). 그 보호는 worker가 번들 interpreter라는 것과 번들 Python의 `EXTERNALLY-MANAGED` 표시에
  기대고, 사용자에게는 "Aelix extension manager failed"만 보인다. 어댑터가 이 명령을 알아보고 Studio 화면으로
  안내하거나 Studio 절차로 넘겨야 한다. 어댑터 자체의 보호는 macOS 경로 문자열 검사 하나뿐이다.
- **대화의 `/extension list` 문구.** 로드된 확장을 "REFUSED … not loaded"로 적는다(5.2).
- **켜고 끄는 권한.** launch에 넣은 확장은 세션이 끌 수 없다(3.3). Studio가 설치한 확장을 자동으로
  launch에 넣으면 #7의 켜기/끄기는 launch 설정을 바꾸는 방식이어야 한다. 대화별로 켜고 끄게 하려면 설치한
  확장을 launch에 넣지 않고 세션 경로를 써야 한다. 둘을 섞으려면 ACP 변경이 필요하다(8.2의 4번).
- **manifest까지 로드하는 정식 방법.** 지금은 링크 디렉터리(3.3)로 된다. 설치된 pack을 지정해 manifest와
  함께 로드하는 인자가 있으면 링크가 필요 없다. aelix-ai #624의 켜기/끄기 저장이 들어온 뒤 `--no-extensions`를
  유지할지도 함께 정한다.

### 7.4 Studio 패키징에서 바꿀 것

- `launch.py`가 세대 `site-packages` 경로를 인자로 받아 `sys.path` 끝에 더한다.
- `launch.cjs`가 `current.json`을 읽고, 묶인 번들이 맞는지 확인하고, lease를 잡고, 세대 경로와
  `--extension` 인자를 붙인다. 맞는 세대가 없으면 지금 그대로 실행한다.
- 번들을 만들 때 번들 Python에 `EXTERNALLY-MANAGED` 표시가 있는지 확인한다(모든 target).
- 번들 Python의 자식이 번들에 `.pyc`를 쓰지 않게 한다. PR #45의 launcher 변경이 이것을 한다. 병합 전에는
  helper가 환경 변수를 준다(`NativeAuthService`가 이미 그렇게 한다).
- native wheel, `native-site`, lock, host는 바꾸지 않는다.

## 8. 결정

### 8.1 이 초안의 기술 제안

ADR을 채택하면 함께 확정되는 구현 방식이다. 사용자에게 보이는 동작을 바꾸는 선택은 8.2로 옮겼다.

1. 설치 위치는 사용자 영역의 venv 세대다.
2. 관리는 세대의 venv interpreter로, 대화는 번들 interpreter에 세대를 더해 `-e`로만 로드한다(5.2).
3. 설치는 후보 세대에서 하고 5.3·5.5를 통과해야 전환한다. 잠금·revision·lease·복구는 5.6을 따른다.
4. 세대는 번들에 묶는다. 번들이 바뀌면 기존 세대를 고치지 않고 새 후보로 옮긴다(5.8).
5. 설치는 Studio helper 서비스가 하고, 화면 모듈은 5.11의 요청만 쓴다.
6. 확장이 없으면 실행 방식은 지금과 같다.

## 10. 확인하지 않은 것

- **Windows.** venv가 사용자 영역에 `python.exe`(launcher 사본)를 만든다. 사용자 쓰기 영역의 실행 파일을
  막는 정책(AppLocker 등)에서 설치가 되는지, 긴 경로, `pywin32` 경로 처리, 링크 디렉터리(junction), 파일
  잠금, console script(`.exe`)의 경로 고치기를 확인해야 한다. 권장한 형태에서는 대화가 사용자 영역의 실행
  파일을 쓰지 않으므로 영향은 설치 작업에 한정된다.
- **Linux.** 실행하지 않았다.
- **다른 target의 `EXTERNALLY-MANAGED` 표시.** macOS arm64 번들에서만 봤다.
- **서명된 설치 앱.** 컴파일된 모듈(`.so`·`.pyd`)이 든 확장의 로드. `entitlements.plist`에 library validation
  해제가 있지만 번들 Python에 적용되는지는 보지 않았다.
- **실제 Studio 업데이트.** 번들 디렉터리를 바꿔치기한 모의다.
- **Python minor가 바뀐 번들.** 감지만 했다.
- **사용자의 터미널 CLI를 실행하는 목록·설치·제거.** 실행하지 않았다.
- **공개 PyPI에서 확장을 이름으로 설치.** 내부 index(loopback)에서 이름 설치를 했고, 공개 PyPI에서는 확장의
  의존성(`tabulate`)만 받았다.
- **컴파일된 모듈이 든 확장, 의존성이 큰 확장.** 순수 Python 확장으로만 실험했다.
- **외부 접속 감사.** Python 소켓 호출 추적까지 했다. kernel 수준 감사(Studio #15)에는 넣지 않았다.
- **main에서 만든 번들.** 시험한 번들은 #31 branch의 것이다. launcher만 main의 것으로 바꿔 일부를 다시
  실행했다. main의 lock으로 만든 번들 전체로는 실행하지 않았다.

2026-11-17, 독립 리뷰(blocking 4, should-fix 5) 반영. 지적을 각각 다시 실행해 확인했고 틀린 지적은 없었다.
