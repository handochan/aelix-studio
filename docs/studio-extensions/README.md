# D04 ADR 초안 — 확장 설치 위치와 관리 runtime 세대

> [Studio #32](https://github.com/handochan/aelix-studio/issues/32)의 D04 spike 결과다. 2026-11-17에
> native pin `e19ab55e`, ACP pin `16d6555b`, Studio main `0665d6004`, macOS arm64에서 확인했다.
> 실험 명령과 출력은 [실험 기록](spike-evidence.md)에 있다.

상태: **Proposed (초안)** · 사용자 확정 전이다. 이 문서는 구현·병합·출시 승인이 아니다.
Windows, Linux, 서명된 설치 앱에서는 실행하지 않았다(10절). 판단의 정본은
[decisions.md](../studio-release-train/decisions.md)의 D04이고, 이 초안이 채택되면 그 표에 반영한다.

각 사실에는 근거를 붙였다. **[실행]** 은 번들 사본에서 돌려 본 것, **[소스]** 는 pin의 소스를 읽은 것,
**[추정]** 은 둘 다 아닌 것이다.

## 1. 결론

- 확장은 **사용자 영역의 얇은 venv 세대**에 설치한다. 세대의 Python은 번들의 Python이고, native와 ACP는
  계속 번들에서 읽는다. 세대에는 확장과, 번들에 없는 의존성만 들어간다.
- 지금 native(`aelix extension … --yes`), 지금 ACP, 수정하지 않은 번들로 다음을 실행해 확인했다: 파일·이름·
  git·내부 index 설치, 업데이트, 제거, 외부 차단 상태의 오프라인 반입, 실패 시 전환하지 않기, 되돌리기,
  번들 교체 뒤 유지. **1단계는 R8 없이 만들 수 있다.**
- 설치는 새 후보 세대에서 하고, 검증을 통과한 뒤에만 "현재 세대"를 가리키는 파일을 바꾼다. 실패하면 후보를
  지운다. 현재 세대는 건드리지 않는다.
- 확장을 하나도 설치하지 않은 사용자는 지금과 똑같이 번들만으로 실행한다.
- overlay 디렉터리 방식은 채택하지 않는다. native가 출처 검사로 거부하고, 우회하면 업그레이드와 제거에서
  설치 기록이 깨졌다.
- 이 방식만으로 풀리지 않는 것이 세 가지 있다. 사용자 결정과 ACP·aelix-ai 요청으로 넘긴다(7·8절).
  1. ACP는 native를 `--no-extensions`로 띄운다. 설치한 확장은 목록에는 보이지만 대화에서는 로드되지 않는다.
     어댑터 인자로 넘기면 로드되지만 manifest로 선언한 기능은 빠진다.
  2. 대화창의 `/extension install`은 실행 중인 세대를 검증 없이 직접 바꾼다.
  3. 진행률과 오류 구분은 종료 코드 네 가지뿐이다. "index에 닿지 못함"과 "이미 최신"을 구분하지 못한다.

## 2. 지켜야 하는 것

이미 확정된 제약이다. 이 초안은 이를 바꾸지 않는다.

- native wheel은 수정하지 않는다(D01). 번들은 설치 뒤 바꾸지 않는다.
- host는 Aelix 전용 메시지를 그대로 넘기고, 전역 관리는 Studio helper가 한다(D05·D17).
- 새 Aelix 화면은 Aion 대화 저장소에 묶지 않는 독립 모듈이다(D20).
- R8이 보류인 동안 설치는 `aelix extension … --yes`를 실행하고 종료 코드로 판단한다.
- 켜기/끄기는 [Studio #7](https://github.com/handochan/aelix-studio/issues/7)이 맡는다.
- Studio를 업데이트해도 설치한 확장이 남는다(G16). 외부가 막힌 환경에서 wheel을 반입할 수 있다(G12).
- 사용자의 시스템 CLI를 임의로 업데이트하지 않는다(D04).

## 3. 확인한 사실

### 3.1 native 설치가 하는 일

pin `e19ab55e` 기준이다. aelix-ai `origin/main`(`bf507d59`)의 `extension_install.py`는 주석 한 줄만 다르다. **[소스]**

### 3.2 지금 번들에서 실행하면

번들은 `python -I -S -B -X utf8 launch.py native …`로 실행한다. `launch.py`가 `native-site`를 `sys.path`
맨 앞에 넣는다.

| 확인                                         | 결과                                                                                                                                                                                 | 근거 |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---- |
| `-I -S`의 효과                               | `sys.path`는 `native-site`와 표준 라이브러리뿐이다. `PYTHONPATH`, user site, 번들 Python의 `site-packages`(pip이 여기 있다), `.pth`는 모두 빠진다                                    | 실행 |
| `uv`가 `PATH`에 없을 때 `extension install`  | 종료 코드 2. "no usable package installer"                                                                                                                                           | 실행 |
| `uv`가 `PATH`에 있을 때                      | 종료 코드 1. uv가 번들 Python의 `EXTERNALLY-MANAGED` 표시를 보고 거부한다                                                                                                            | 실행 |
| 번들 변경                                    | 두 경우 모두 번들 파일은 그대로다(`checksums.json` 대조)                                                                                                                             | 실행 |
| 강제로 설치한다면                            | 번들 Python의 `site-packages`에 들어간다. 번들을 바꾸게 되고, `-S` 때문에 실행 때 보이지도 않는다                                                                                    | 추정 |
| `native-site`에 entry point 확장을 넣어 배포 | 지금 실행 방식에서는 `native-site`가 설치 디렉터리 목록에 없다. entry point 확장을 번들에 넣어도 거부된다. 지금 번들에는 그런 확장이 없고 Analytics는 `-e` 경로로 로드해 영향이 없다 | 실행 |
| `python -m venv`를 `-B`만 주고 실행          | 자식 프로세스(ensurepip)가 번들 표준 라이브러리에 `.pyc` 166개를 썼다. 환경 변수 `PYTHONDONTWRITEBYTECODE=1`을 같이 주면 0개다                                                       | 실행 |

### 3.3 ACP가 하는 일

Studio 대화는 ACP 어댑터가 띄운 native worker에서 돈다. 이 부분은 결정 문서와 Issue에 적혀 있지 않았다.

- 어댑터는 worker를 `--mode rpc --offline --no-extensions`로 시작하고, 명시한 것만 `-e`로 넘긴다
  (Analytics 확장, `--extension` 인자, 세션에서 켠 것, 승인 브리지). **[소스]**
- 그래서 대화에서는 pip으로 설치한 확장도, 사용자의 전역 디렉터리 확장도 로드되지 않는다. 세대에 설치한
  확장은 `/extension list`에 나오지만 그 확장의 `/hello`는 "Unknown slash command"였다. **[실행]**
- 어댑터 시작 인자에 `--extension aelix_starter:setup`(entry point 값) 또는 세대 안의 패키지 디렉터리를
  주면 `/hello`가 광고되고 실행됐다. 번들만으로 같은 인자를 주면 "No module named"였다. **[실행]**
- 이렇게 `-e`로 넘긴 확장은 두 형태 모두 **manifest 없이** 로드된다. 코드로 등록하는 명령·도구는 되지만
  `aelix-plugin.toml`로 선언한 기여(MCP 서버·테마·hook)와 capability 검사는 적용되지 않는다. manifest를 묶는
  것은 entry point 경로뿐이고 `--no-extensions`가 그 경로를 끈다. **[소스]**
- 어댑터에는 대화용 `/extension install|update|remove|list|verify` 등이 이미 있다. 승인 요청 뒤
  `aelix extension …`을 실행한다. 실행 파일은 `--extension-manager`가 있으면 그것, 없으면 worker의
  interpreter다. 쓰기 동작은 실행 파일 경로에 `.app/Contents/`가 들어 있을 때만 막는다. **[소스]**
- worker가 세대 interpreter로 돌 때 대화에서 `/extension install <0.2.0 wheel>`을 승인하니 **현재 세대가
  그 자리에서 0.1.0에서 0.2.0으로 바뀌었다.** 후보·검증·전환을 거치지 않는다. **[실행]**

| ---------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| 얇은 venv 세대         | 사용자 영역에 번들 Python으로 venv를 만든다. native는 번들에서 읽고 확장만 venv에 설치한다 | native CLI가 설계된 대로 동작했다(pip, 설치 디렉터리 인정, 제거, 목록). 3.1의 명령 전부와 5절의 절차를 실행했다. 번들은 끝까지 그대로였다                                                                                                                                                                                                                                  | **권장**                          |
| overlay 디렉터리       | 번들 Python을 그대로 쓰고 사용자 영역 디렉터리 하나를 import 경로에 더한다                 | `sys.path`에만 더하면 native가 "REFUSED (untrusted sys.path provenance)"로 거부했다. `PYTHONUSERBASE`로 user site인 것처럼 알리면 통과했다. native CLI로 설치하려면 pip을 환경 변수로 돌려야 했다. 업그레이드하니 pip이 패키지 디렉터리를 바꾸지 않았고 0.1.0과 0.2.0 기록이 함께 남았는데 종료 코드는 0이었다. 제거한 뒤에는 기록만 남은 "manifest not bound" 항목이 됐다 | 제외. native 지원이 생기면 재검토 |
| 전체 복제 환경         | 사용자 영역에 native wheel까지 넣은 독립 환경을 만들고 거기서 실행한다                     | 실행하지 않았다. 번들에는 wheel 파일이 없고 설치된 트리만 있다. 실행 코드가 서명·목록 밖의 사용자 쓰기 영역으로 옮겨지고, pip이 native 의존성을 바꿀 수 있다                                                                                                                                                                                                               | 제외                              |
| 사용자 CLI 환경에 설치 | Studio가 사용자의 터미널 `aelix`가 쓰는 환경에 직접 설치한다                               | 실행하지 않았다. D04가 시스템 CLI 임의 업데이트를 제외했다. Studio runtime은 그 환경의 패키지를 볼 수 없다(6절)                                                                                                                                                                                                                                                            | 1단계 제외. 사용자 결정(8.2)      |

overlay가 통과한 `PYTHONUSERBASE` 경로는 `-I`가 그 변수를 무시한다는 문서와 달리 `site.getusersitepackages()`가
환경 변수를 직접 읽기 때문에 생긴다. Python이 고치면 사라질 동작이라 설계 근거로 쓰지 않는다. **[실행·추정]**

## 5. 권장 설계

### 5.1 위치와 구성

Studio 사용자 데이터 디렉터리 아래에 둔다. 앱 번들, 사용자의 CLI 환경, CLI와 공유하는 `~/.aelix` 어디에도
쓰지 않는다. 정확한 디렉터리 이름은 구현에서 정한다.

```text
<Studio 사용자 데이터>/aelix-runtime/
  current.json                 현재 세대, 이전 세대, 묶인 번들 정보
  constraints-<lock>.txt       번들에 설치된 배포판과 버전(번들에서 계산)
  generations/<id>/
    venv/                      번들 Python으로 만든 venv. 확장과 추가 의존성만 들어간다
    agent/                     native 설치 기록과 pin (세대와 함께 복제·폐기)
    generation.json            설치 내역, 검증 결과, 묶인 번들 정보
```

- 세대는 번들의 `target`, Python minor 버전, `dependencyLockSha256`, native commit에 묶는다(번들
  `manifest.json`에서 읽는다). D04의 "bundled source/ABI/lock에 연결"이 이것이다.
- 세대 하나는 약 12MB였다. 거의 전부 세대마다 들어가는 pip이다. 현재와 이전 두 개를 남긴다. **[실행]**

### 5.2 실행

- 세대가 없으면 지금과 같다: `<번들>/python -I -S -B -X utf8 launch.py native …`.
- 세대가 있으면 interpreter만 바꾸고 `-S`를 뺀다:
  `<세대>/venv/bin/python -I -B -X utf8 <번들>/launch.py native …`.
  `sys.path`는 `native-site`, 표준 라이브러리, 세대 `site-packages` 순서다. 번들이 항상 이긴다. **[실행]**
- `-S`를 빼야 한다. Python 3.12는 venv 인식을 `site` 모듈이 한다. `-S`를 두면 `sys.prefix`가 번들을
  가리켜 pip도, 설치 디렉터리 인정도 없다. **[실행]**
- ACP는 번들 그대로 실행하고 인자만 더한다. 수정하지 않은 `launch.cjs`가 인자를 그대로 넘겨 동작했다: **[실행]**
  `node launch.cjs --aelix <세대 python> --aelix-arg=-I --aelix-arg=-B --aelix-arg=-Xutf8 --aelix-arg=<번들>/launch.py --aelix-arg=native --extension <확장>`.
- 세대 경로는 설치할 때마다 바뀐다. host 설정에 저장된 실행 인자에 세대 경로를 넣지 않는다. Studio가 소유한
  `launch.cjs`가 시작할 때 `current.json`을 읽어 위 인자를 만든다. host는 바꾸지 않는다(D17).
  이 변경은 번들 구성 변경이라 다른 작업과 직렬로 한다. **[추정: 인자 전달은 실행했고, 읽는 코드는 아직 없다]**
- 실행 중인 어댑터는 시작할 때의 세대를 계속 쓴다. 새 세대는 새 세션부터 적용한다.

### 5.3 설치·업데이트·제거 절차

1. 후보 세대를 만든다. 번들 Python으로 venv를 만들고(오프라인, 1.3–2.0초) 현재 세대의 `site-packages`와
   `agent/`를 복사한다.
2. 후보에서 native CLI를 실행한다: `--offline`(반입일 때) `extension install|update|remove <대상> --yes`.
3. 종료 코드가 0이 아니면 후보를 지운다.
4. 검증한다(5.4). 하나라도 실패하면 후보를 지운다.
5. `generation.json`을 쓰고 `current.json`을 임시 파일에 쓴 뒤 rename으로 바꾼다.

native CLI에 넘기는 환경이다. 부모(`-I`)는 `PYTHON*`을 무시하고 pip 자식만 읽는다. **[실행]**

| 환경 변수                             | 이유                                                                                                                                   |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `AELIX_CODING_AGENT_DIR=<세대>/agent` | native가 설치 기록을 CLI와 공유하는 `~/.aelix/agent/settings.json`에 쓰지 않게 한다. 버린 후보의 기록도 함께 사라진다                  |
| `PYTHONPATH=<번들>/native-site`       | pip이 번들에 이미 있는 패키지를 설치된 것으로 본다. 없으면 pip은 번들에 무엇이 있는지 모른다                                           |
| `PIP_CONSTRAINT=<constraints URL>`    | 번들과 다른 버전을 요구하는 확장을 설치 단계에서 실패시킨다. 없으면 pip이 다른 버전을 세대에 깔고, 실행 때는 번들 버전이 조용히 이긴다 |
| `PYTHONDONTWRITEBYTECODE=1`           | 번들 표준 라이브러리에 `.pyc`가 생기지 않게 한다(3.2)                                                                                  |
| `PIP_DISABLE_PIP_VERSION_CHECK=1`     | pip이 스스로 PyPI에 버전을 묻지 않게 한다                                                                                              |
| `PIP_NO_INDEX=1`, `PIP_FIND_LINKS`    | 오프라인 반입(5.7)                                                                                                                     |
| `PIP_INDEX_URL`                       | `update`에는 `--index-url`이 없어 이 변수로 내부 index를 준다                                                                          |

`PIP_CONSTRAINT`와 `PIP_FIND_LINKS`는 공백으로 값을 나눈다. "Application Support"처럼 공백이 있는 경로는
깨졌고, `file://` URL로 주니 공백과 한글 경로에서 동작했다. **[실행]**

### 5.4 전환 전 검증

| 검사                                                      | 실패 예 (실행한 것)                                                                                              |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| native 종료 코드 0                                        | 번들과 충돌하는 의존성(`packaging<24`, 번들 26.3): pip `ResolutionImpossible`, 종료 코드 1                       |
| 세대에 번들과 같은 이름의 배포판이 없다                   | constraints를 뺀 설치: pip은 성공(0)하고 `packaging 23.2`를 세대에 깔았다. 이 검사가 잡았다                      |
| 세대에 `.pth` 파일이 없다                                 | 실행한 실패 예 없음. 번들 검사(`bundle.py`)와 같은 기준이다                                                      |
| `aelix extension verify` 종료 코드 0                      | manifest가 묶이지 않으면 1                                                                                       |
| `aelix --offline status --json`에 오류가 없고 대상이 있다 | import할 수 없는 0.3.0으로 업데이트: native는 0을 돌려줬고, 이 검사가 "No module named …"를 잡아 전환하지 않았다 |

native 종료 코드 0은 "설치됐다"이지 "import된다"가 아니다. 마지막 검사가 완료 조건의 "실제 import까지 확인"이다.

### 5.5 되돌리기와 정리

- 실패한 작업은 전환 자체를 하지 않으므로 되돌릴 것이 없다. **[실행]**
- 사용자가 직전 상태로 되돌릴 때는 `current.json`을 이전 세대로 바꾼다. 0.2.0에서 0.1.0으로, 다시 0.2.0으로
  바꿔 `status`로 확인했다. **[실행]**
- 정리는 앱 시작 때 한다. 현재와 이전 세대를 남기고 나머지를 지운다. 실행 중인 어댑터가 쓰는 세대는 지우지
  않는다. **[추정: 구현하지 않았다]**

### 5.6 Studio 업데이트 (G16)

세대는 앱 밖에 있어 번들을 교체해도 남는다. 번들이 바뀌면 시작할 때 묶인 정보를 비교한다.

| 새 번들                                     | 처리                                                                                                                                          | 확인                                                           |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 경로만 다르다(같은 Python, 같은 lock)       | venv의 `pyvenv.cfg`와 interpreter 링크를 새 경로로 고치고 다시 검증한다                                                                       | 실행. 옛 번들을 지운 뒤 링크가 끊겼고, 고친 뒤 확장이 로드됐다 |
| lock이나 native가 다르다(같은 Python minor) | 다시 검증한다. 통과하면 그대로 쓴다. 실패하면 새 번들 기준으로 세대를 다시 만든다: 빈 후보에 설치 기록을 순서대로 다시 설치하고 검증·전환한다 | 실행(모의). 번들이 `tabulate`를 싣게 된 경우를 만들었다        |
| Python minor가 다르다                       | 세대를 다시 만든다. 컴파일된 모듈이 든 wheel은 새 버전용을 다시 받아야 한다                                                                   | 감지만 실행. 3.13 번들이 없어 다시 만들기는 실행하지 않았다    |

- 다시 만들 수 없으면(오프라인, 출처 없음) 번들만으로 시작하고 "다시 설치 필요"로 표시한다. 옛 세대는 지우지 않는다.
- 다시 만들려면 출처가 있어야 한다. 파일로 반입한 wheel은 Studio가 사용자 영역에 사본을 보관한다. 이름으로
  설치한 것은 index에 다시 접속한다. **[추정: 사본 보관은 구현하지 않았다]**
- CLI와 공유하는 `~/.aelix`는 이 과정에서 읽지도 쓰지도 않는다. G16의 "공유 원본은 보존"과 맞는다.

### 5.7 오프라인 wheel 반입 (G12)

macOS sandbox로 모든 네트워크를 막고 실행했다. **[실행]**

- 사용자가 wheel 파일(또는 wheel이 든 폴더)을 고른다. Studio는 `--offline`과 `PIP_NO_INDEX=1`,
  `PIP_FIND_LINKS=<반입 폴더>`로 설치한다.
- 의존성이 없는 wheel: 성공. 의존성이 같은 폴더에 있는 wheel: 성공. 의존성이 없는데 폴더에도 없는 wheel:
  약 2초 만에 종료 코드 1로 끝났고 현재 세대는 그대로였다.
- venv 만들기도 오프라인이다. 번들 Python에 든 pip wheel을 쓴다.
- **native의 `--offline`만으로는 부족하다.** `PIP_NO_INDEX` 없이 `aelix --offline extension install <wheel>`을
  실행하니 pip이 빠진 의존성을 PyPI에서 받았다(네트워크를 연 상태에서 확인). aelix-ai에 알린다(7.2).
- 내부 index는 loopback의 index만 허용한 sandbox에서 이름 설치와 업데이트를 실행했다.

### 5.8 외부 접속

- 확장 화면을 열거나 목록을 보는 것만으로는 접속하지 않는다. 설치·업데이트를 사용자가 실행할 때만, 사용자가
  정한 index나 git 주소로 pip 자식 프로세스가 접속한다.
- 파일 반입은 접속이 0이다(5.7).
- `aelix extension discover`는 쓰지 않는다. 기본 catalog(`handochan.github.io/aelix-marketplace`)를 받아
  온다. **[소스·실행: `extension source list`에 기본 catalog가 나온다]**
- 설치한 확장의 코드가 실행 중에 하는 접속은 Studio가 막지 못한다.
- 이 접속은 [외부 접속 목록](../studio-outbound/README.md)에 "사용자가 명시한 endpoint"로 추가해야 한다.
  감사 시나리오에서 설치를 실행하지 않으면 접속은 없다. Studio #15와 맞춘다. **[추정]**

### 5.9 실행 주체와 화면 모듈 인터페이스

- 설치는 **Studio helper 서비스**가 한다. Provider 설정이 쓰는 `NativeAuthService`
  (`packages/web-host/src/studio-auth/`)와 같은 자리, 같은 방식이다. 데스크톱은 IPC로, WebUI는 로그인한
  사용자의 요청으로 부른다. 세대 interpreter를 argv로 직접 실행하고 shell을 쓰지 않는다.
- host와 ACP를 거치지 않는다. 실행 중인 worker를 건드리지 않는다(D05·D17). 변경은 한 번에 하나만 한다.
- 화면 모듈(D20)은 아래 요청만 안다. pip, venv, 세대 경로는 모른다.

| 요청                                                      | 응답                                                                                                                                                        |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list`                                                    | 현재·이전 세대 ID, 적용 시점(새 세션), 확장별 이름·배포판·버전·출처·상태(준비됨 / manifest 미결합 / 로드 오류 / 다시 설치 필요), CLI 쪽 읽기 전용 항목(6절) |
| `install` (이름+index \| 파일·폴더 \| git, 오프라인 여부) | 작업 ID                                                                                                                                                     |
| `update` / `remove` (이름)                                | 작업 ID                                                                                                                                                     |
| `rollback`                                                | 바뀐 현재 세대                                                                                                                                              |
| `poll` / `cancel` (작업 ID)                               | 단계(준비 / 설치 / 검증 / 전환됨 / 실패 / 취소됨), 실패 코드, 설치 도구 출력의 끝부분(길이 제한)                                                            |

실패 코드는 지금 정보로 낼 수 있는 것만 둔다: 설치 도구 실패, 실행 안 됨, manifest 미결합, 번들과 충돌,
로드 오류, 변경 없음. 세부 사유는 pip 출력 문장뿐이다.

## 6. 사용자 CLI에 이미 있는 확장

Studio runtime은 CLI와 agent dir(`~/.aelix/agent`)을 공유하지만 Python 환경은 따로다.

| 종류                                       | 지금 Studio가 보는 것                                                                                                                                  | 권장 처리                                                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| 전역 디렉터리 `~/.aelix/agent/extensions/` | 번들 native를 CLI처럼 실행하면 로드된다. 번들에 없는 패키지를 import하는 확장은 오류가 난다. **대화(ACP)에서는 로드되지 않는다** [실행]                | 읽기 전용으로 보여 준다. 대화에서 켜는 것은 #7의 켜기/끄기로 다룬다. Studio가 이 디렉터리를 고치지 않는다 |
| 프로젝트 `.aelix/extensions/`              | 위와 같다. 프로젝트 신뢰가 있어야 한다 [소스]                                                                                                          | 이 카드에서 다루지 않는다                                                                                 |
| CLI 환경에 pip으로 설치한 확장             | **보이지 않는다.** `extension list`는 비어 있다. 공유 `settings.json`의 설치 기록만 `extension source list`에 보인다 [실행]                            | 기록을 읽어 "CLI에 설치 기록 있음"으로 보여 주고, 사용자가 고르면 Studio 세대에 같은 출처로 설치한다      |
| 기록의 교차 영향                           | agent dir을 공유한 채 설치하면 Studio의 설치가 CLI 기록에 섞인다. 한쪽에서 이름 없이 `extension update`를 하면 다른 쪽이 기록한 확장까지 깔린다 [실행] | Studio는 세대별 `agent/`에 기록한다(5.3). 이름 없는 `update`를 쓰지 않는다                                |

CLI 환경에 실제로 무엇이 깔려 있는지는 사용자의 `aelix extension list`를 실행해야 알 수 있다. 읽기만 하는
실행이지만 사용자의 CLI를 Studio가 실행하는 일이라 사용자 결정으로 둔다(8.2).

### 7.1 지금 되는 것 (`--yes`와 종료 코드)

설치(파일·이름·git·내부 index), 업데이트, 제거, 오프라인 반입, 검증 뒤 전환, 되돌리기, 번들 교체 뒤 유지.
목록과 로드 확인은 `extension list`·`verify`·`status --json`으로 한다. 모두 실행했다.

### 7.2 aelix-ai에 필요한 것

R8의 내용을 구체적으로 적으면 아래와 같다. 1단계를 막지 않는다.

| 빠진 것                                                                                                       | 지금의 대체                                          | 근거 |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ---- |
| 기계가 읽는 결과: 무엇이 어떤 버전으로 설치·제거됐는지, 오류 종류(네트워크·의존성 충돌·빌드 실패·해시 불일치) | 종료 코드와 설치 전후 장부 비교, pip 출력 문장       | 소스 |

| 설치 위치와 constraints 지정, 번들 패키지 인식                                                                | venv와 환경 변수(5.3)                                | 실행 |
| 제거할 때 남는 의존성 정리                                                                                    | 없음. `extension remove tabulate`는 종료 코드 2였다  | 실행 |

R8과 별개로 버그로 알릴 것이 두 가지다.

- `aelix --offline extension install <경로>`가 빠진 의존성을 공개 index에서 받는다(5.7). **[실행]**
- `extension remove`만 pip의 종료 코드를 그대로 돌려준다. 다른 동작의 0/1/2/3 구분과 다르다. **[소스]**

### 7.3 ACP에 필요한 것

- **대화의 `/extension install|update|remove`.** 지금은 worker의 환경을 그 자리에서 바꾼다(3.3). Studio가
  관리하는 세대에서는 이 동작을 Studio 화면으로 넘기거나 막아야 한다. 어댑터의 보호는 macOS 경로 문자열 검사
  하나뿐이다. `--extension-manager`는 접두 인자 없는 실행 파일 하나만 받는데, 세대에는 `aelix` 실행 파일이
  없다. Studio 쪽에서 우회하지 않고 ACP 변경으로 요청한다.
- **설치한 확장을 대화에서 manifest까지 로드하는 방법.** 지금은 어댑터 시작 인자 `--extension`뿐이고
  manifest가 빠진다(3.3). entry point 경로만 켜는 방법이 native에 없다. aelix-ai #624의 켜기/끄기 저장이
  들어오면 `--no-extensions`를 유지할지, 설치된 확장만 고르는 인자를 둘지는 ACP·aelix-ai와 #7에서 정한다.

### 7.4 Studio 패키징에서 바꿀 것

- `launch.cjs`(또는 `launch.py`)가 `current.json`을 읽어 세대 interpreter 인자를 붙인다. 8.2의 3번이
  정해지면 설치된 확장의 `--extension` 인자도 붙인다.
- 세대로 실행할 때 `-S`를 뺀다. 세대가 없을 때는 지금 그대로다.
- native wheel, `native-site`, lock, host는 바꾸지 않는다.

## 8. 결정

### 8.1 이 초안이 제안하는 것 (사용자 확정 대상)

1. 설치 위치는 사용자 영역의 얇은 venv 세대다. overlay·전체 복제·CLI 환경 직접 설치는 1단계에서 제외한다.
2. 설치는 후보 세대에서 하고 5.4의 검증을 통과해야 전환한다. 현재와 이전 세대를 남긴다.
3. 세대는 번들의 target·Python minor·lock·native commit에 묶는다. 번들과 버전이 충돌하는 의존성은 설치를
   거부한다.
4. native 설치 기록은 세대별로 두고 CLI와 공유하는 `~/.aelix`에는 쓰지 않는다.
5. 설치는 Studio helper 서비스가 하고, 화면 모듈은 5.9의 요청만 쓴다.
6. 확장이 없으면 실행 방식은 지금과 같다.

## 10. 확인하지 않은 것

- **Windows.** venv가 사용자 영역에 `python.exe`(launcher 사본)를 만든다. 사용자 쓰기 영역의 실행 파일을
  막는 정책(AppLocker 등)에서 실행되는지, 긴 경로, `pywin32` 경로 처리와 함께 도는지 확인해야 한다.
- **Linux.** 실행하지 않았다.
- **서명된 설치 앱.** 번들 Python을 사용자 영역의 링크로 실행하는 것, 컴파일된 모듈(`.so`·`.pyd`)이 든 확장의
  로드. `entitlements.plist`에 library validation 해제가 있지만 번들 Python에 적용되는지는 보지 않았다.
- **실제 Studio 업데이트.** 번들 디렉터리를 바꿔치기한 모의다.
- **Python minor가 바뀐 번들.** 감지만 했다.
- **공개 PyPI에서 확장을 이름으로 설치.** 내부 index(loopback)에서 이름 설치를 했고, 공개 PyPI에서는 확장의
  의존성(`tabulate`)만 받았다.
- **컴파일된 모듈이 든 확장, 의존성이 큰 확장.** 순수 Python 확장 세 개로만 실험했다.
- **두 Studio 프로세스의 동시 변경.** 잠금을 구현하지 않았다.
