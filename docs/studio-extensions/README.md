# D04 ADR — 확장 설치 위치와 관리 runtime 세대

> [Studio #32](https://github.com/handochan/aelix-studio/issues/32)의 D04 spike 결과다. 2026-11-17에
> native pin `e19ab55e`, ACP pin `16d6555b`, macOS arm64에서 확인했다. 같은 날 독립 리뷰를 세 번 받아 고쳤다
> (11절). 실험 명령과 출력은 [실험 기록](spike-evidence.md)에 있다.

상태: **설치 방식 채택(2026-11-17 사용자 결정, 8.2의 A1)** · 설치 helper 구현을 시작하고 화면에는 아직 내지
않는다. 같은 날 A2·A3·A4·A10·A11·A12도 정해졌다. 2026-11-19에 A5·A6·A7을 정했다. A8·A9는 미정이다.
초기 실험은 macOS 번들 사본에서 수행했다. OS별 설치 앱 확인은 9절의 1a′를 따른다. 이 문서는 병합·출시 승인이
아니다. 구현·병합·출시는 각 Issue와 저장소 규칙을 따른다. 판단의 정본은
[decisions.md](../studio-release-train/decisions.md)의 D04와 기록이다.

각 사실에는 근거를 붙였다. **[실행]** 은 번들 사본에서 돌려 본 것, **[소스]** 는 pin의 소스를 읽은 것,
**[추정]** 은 둘 다 아닌 것이다. 시험한 번들 사본은 main이 아니라 Studio #31 branch에서 준비한 것이다.
main과 다른 점과 그 영향은 3.2와 실험 기록에 적었다.

## 1. 결론

- 확장은 **사용자 영역의 얇은 venv 세대**에 설치한다. 세대에는 확장과, 번들에 없는 의존성만 들어간다.
  native와 ACP는 계속 번들에서 읽는다.
- 실행 형태를 둘로 나눈다(5.2).
  - **관리**(설치·업데이트·제거·목록): 세대의 venv interpreter로 native CLI를 실행한다. native CLI는 venv
    안에서만 설계대로 동작한다.
  - **대화**: 지금처럼 번들의 interpreter를 `-I -S`로 실행하고, launcher가 세대의 `site-packages`를 import
    경로 끝에 더한다. 확장은 `-e`로 명시한 것만 로드한다.
- 설치는 새 후보 세대에서 하고, 검증을 통과한 뒤에만 "현재 세대"를 가리키는 파일을 바꾼다. 검증은 요청한
  대상이 결과에 있는지 대조하고, 대화와 같은 형태로 native를 띄워 기대한 확장이 모두 로드됐는지 묻는다(5.5).
  실패하면 후보를 지운다.
- 확장을 하나도 설치하지 않은 사용자는 지금과 똑같이 번들만으로 실행한다.
- **만들 수 있는 것과 사용자에게 낼 수 있는 것은 다르다.**
  - 설치 helper(세대 만들기·설치·검증·전환·되돌리기)는 지금 native와 지금 ACP로 만들 수 있다. R8이 필요
    없다. 파일·이름·git·내부 index 설치, 업데이트, 제거, 오프라인 반입, 번들 교체 뒤 유지를 실행해 봤다.
  - 화면으로 내려면 **ACP가 대화창의 설치·업데이트·제거를 명시적으로 막거나 Studio로 넘겨야 한다**(7.3).
    Studio 쪽 실행 형태만으로는 막히지 않는다. 그 밖에 켜고 끄는 단위(Studio #7), launcher 변경,
    Windows·Linux 확인이 선행이다(9절).
- **이 설계가 보장하지 못하는 것**을 구분해 적었다.
  - 대화창 설치의 차단. 환경 변수 하나로 세대나 번들에 설치됐다(3.3).
  - 온라인 설치에서 "지정한 index에만 접속"(5.10).
  - 설치한 확장의 코드가 하는 접속. 전환 전 로드 검증도 확장의 `setup()`을 실행한다(5.9).
  - 오프라인 반입에서 설치 도구가 접속하지 않는 것은 정적 검사와 설정으로 만든다. 증명은 출시 후보의 외부
    접속 감사가 실행한 시나리오에 한정된다(5.9).
- overlay 디렉터리에 native CLI로 설치하는 방식은 채택하지 않는다. native가 출처 검사로 거부하고, 우회하면
  업그레이드와 제거에서 설치 기록이 깨졌다.

## 2. 지켜야 하는 것

이미 확정된 제약이다. 이 문서는 이를 바꾸지 않는다.

- native wheel은 수정하지 않는다(D01). 번들은 설치 뒤 바꾸지 않는다.
- host는 Aelix 전용 메시지를 그대로 넘기고, 전역 관리는 Studio helper가 한다(D05·D17).
- 새 Aelix 화면은 Aion 대화 저장소에 묶지 않는 독립 모듈이다(D20).
- R8이 보류인 동안 설치는 `aelix extension … --yes`를 실행하고 종료 코드로 판단한다.
- 켜기/끄기는 [Studio #7](https://github.com/handochan/aelix-studio/issues/7)이 맡는다.
- Studio를 업데이트해도 설치한 확장이 남는다(G16). 외부가 막힌 환경에서 wheel을 반입할 수 있다(G12).
- 사용자의 시스템 CLI를 임의로 업데이트하지 않는다(D04). 사용자가 동의한 설치까지 금지한 것은 아니다.
- 첫 Beta 필수 항목은 줄이지 않는다. 줄이려면 사용자 승인이 필요하다(decisions.md 사용자 결정 기록).

## 3. 확인한 사실

### 3.1 native 설치가 하는 일

pin `e19ab55e` 기준이다. aelix-ai `origin/main`(`d369ab79`, 2026-11-17)의 `extension_install.py`는 주석 한 줄만
다르다. **[소스]**

| 항목        | 내용                                                                                                                                                                                                                                                         | 근거               |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------ |
| 명령        | `aelix extension install <경로 \| git URL \| 이름[==버전]> [--yes] [--index-url URL] [--offline]`, `update [<이름>] [--yes] [--offline]`, `remove <이름> [--yes]`, `list`, `verify`. `update`에는 `--index-url`이 없다                                       | 소스·실행          |
| 설치 대상   | **실행 중인 interpreter(`sys.executable`)의 환경**이다. 위치를 고르는 인자가 없다. 다만 pip의 환경 변수와 설정 파일이 위치를 바꾼다. 사용자 pip 설정에 `[install] target`이 있으니 파일이 다른 곳에 깔렸고 native는 0을 돌려줬다                             | 소스·실행          |
| 설치 도구   | pip을 import할 수 있으면 pip. 아니면 `PATH`의 `uv`(절대 경로일 때만). 둘 다 없으면 설치하지 않고 종료 코드 2                                                                                                                                                 | 소스·실행          |
| 실행 방식   | 자식 프로세스 `sys.executable -P -m pip install <대상>`. 부모의 환경 변수와 pip 설정을 물려받는다. 의존성은 pip이 푼다                                                                                                                                       | 소스·실행          |
| 설치 기록   | `<agent dir>/settings.json`의 `extensionSources`와 `<agent dir>/extension_pins.json`에 쓴다. **환경별이 아니라 agent dir별**이다. 이름 없는 `extension update`는 기록된 것을 전부 지금 환경에 다시 설치한다                                                  | 소스·실행          |
| 종료 코드   | 0 설치됨, 1 설치 도구가 실패함, 2 설치 도구를 실행하지 않음(인자 오류·거부·설치 도구 없음), 3 설치됐지만 manifest가 묶이지 않음. `remove`만 pip의 코드를 그대로 돌려준다                                                                                     | 소스. 0·1·2는 실행 |
| 시작 시     | 로더가 `sys.path`의 `*.dist-info`에서 entry point 그룹 `aelix.extensions`를 찾는다. 배포판이 interpreter의 설치 디렉터리(`purelib`·`platlib`·`site.getsitepackages()`·user site) 밖에 있으면 **거부한다**. `--trust-extension-path <배포판>`만 예외를 만든다 | 소스·실행          |
| 지연 활성화 | manifest의 활성화 조건이 `on_command`뿐인 pack은 시작할 때 **import하지 않고** 목록에만 넣는다. 그 명령을 처음 쓸 때 import와 `setup()`을 한다                                                                                                               | 소스·실행          |
| 목록        | `extension list`와 control-v1 `extensions/list`는 설치 장부(entry point)를 읽는다. `extensions/list`는 이름·배포판·버전·entry만 준다. 로드 여부나 오류는 없다                                                                                                | 소스·실행          |
| 로드 확인   | `aelix [--offline] status --json`이 세션과 모델 없이 로더를 돌려 `discovered_extensions`와 `extension_errors`를 낸다. **모든 확장의 import를 보장하지는 않는다.** import가 깨진 지연 활성화 pack이 오류 없이 목록에 나왔다                                   | 소스·실행          |
| 요구 사항   | pip(또는 uv), 쓸 수 있는 환경. git 설치는 `git`. wheel이 아닌 소스(git·sdist)는 빌드 도구를 index에서 받고 빌드 코드를 실행한다                                                                                                                              | 실행               |

번들은 `python -I -S -B -X utf8 launch.py native …`로 실행한다. `launch.py`가 `native-site`를 `sys.path`
맨 앞에 넣는다.

| `uv`가 `PATH`에 없을 때 `extension install`  | 종료 코드 2. "no usable package installer"                                                                                                                                                                                                                                                    | 실행 |

| 번들 변경                                    | 두 경우 모두 번들 파일은 그대로다(`checksums.json` 대조)                                                                                                                                                                                                                                      | 실행 |

### 3.3 ACP가 하는 일

Studio 대화는 ACP 어댑터가 띄운 native worker에서 돈다. 이 부분은 결정 문서와 Issue에 적혀 있지 않았다.

- 어댑터는 worker를 `--mode rpc --offline --no-extensions`로 시작하고, 명시한 것만 `-e`로 넘긴다
  (Analytics 확장, `--extension` 인자, 세션에서 켠 것, 승인 브리지). **[소스]**
- 그래서 대화에서는 pip으로 설치한 확장도, 사용자의 전역 디렉터리 확장도 로드되지 않는다. 세대에 설치한
  확장은 `/extension list`에 나오지만 그 확장의 `/hello`는 "Unknown slash command"였다. **[실행]**
- 어댑터 인자 `--extension`으로 넘기면 로드된다. 넘기는 형태에 따라 결과가 다르다. **[실행]**

  | `--extension`에 주는 것                          | 결과                                                                                                                                                                                       |
  | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | 모듈 참조(entry point 값, `aelix_starter:setup`) | 시작할 때 import하고 `setup()`을 실행한다. **manifest 없이** 로드된다. 코드로 등록하는 명령·도구는 되고, manifest로 선언한 MCP 서버·테마·hook과 capability 검사는 빠진다                   |
  | 세대 안의 패키지 디렉터리                        | 위와 같다. 그 디렉터리의 `__init__.py`를 파일로 로드한다                                                                                                                                   |
  | pack마다 링크 하나를 둔 디렉터리                 | **manifest가 결합된다**(확장 이름이 plugin id로 나오고 지연 활성화가 적용된다). 디렉터리 안의 하위 디렉터리를 manifest pack으로 읽는 native 동작이다. entry point 로드와 같지는 않다(아래) |

- 링크 디렉터리 경로에는 entry point 정보가 없다. 그래서 manifest에 `[plugin.entry] python`이 없고 entry
  point가 대신 callable을 지정하는 pack은 로드되지 않거나 hook만 붙는다. entry point가 클래스를 가리키는
  pack은 CLI에서는 `Cls()(api)`로, `-e` 경로에서는 `Cls(api)`로 호출된다. manifest가 선언한 MCP 서버는 시작할
  때 따로 처리되고 거부는 경고로만 남는다. 선언한 MCP 서버·테마·hook이 실제로 동작하는지는 실행하지
  않았다. **[소스]**
- `--extension`으로 넘긴 확장은 어댑터의 launch 설정 소유가 된다. 세션에서 `/extension disable`을 하면
  `-32004 extension_owned_by_launch`로 거부한다. launch에 넣지 않은 확장은 세션이 `/extension enable`·
  `disable`로 켜고 끈다(승인 요청 뒤 worker 재시작). **[실행]**
- 어댑터에는 대화용 `/extension install|update|remove|list|verify` 등이 이미 있다. 승인 요청 뒤
  `aelix extension …`을 실행한다. 실행 파일은 `--extension-manager`가 있으면 그것, 없으면 worker의
  interpreter다. 쓰기 동작은 실행 파일의 실제 경로에 `.app/Contents/`가 들어 있을 때만 막는다. **[소스]**
- 대화의 `/extension install <wheel>`을 승인했을 때의 결과는 worker를 무엇으로 띄웠는지에 달려 있다. **[실행]**

  | worker                                                                      | 결과                                                                                                                                   |
  | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
  | 세대의 venv interpreter                                                     | **현재 세대가 그 자리에서 0.1.0에서 0.2.0으로 바뀌었다.** 후보·검증·전환을 거치지 않는다                                               |
  | 번들 interpreter(`-I -S`) + 세대 `site-packages` 추가, 환경에 pip 변수 없음 | 실패한다("Aelix extension manager failed"). pip이 번들 Python의 `EXTERNALLY-MANAGED`를 보고 거부한다. 세대는 그대로다. `remove`도 같다 |
  | 위와 같고 어댑터 환경에 `PIP_TARGET=<세대 site-packages>`                   | **세대에 설치됐다.** pip은 target을 주면 `EXTERNALLY-MANAGED` 검사를 하지 않는다                                                       |
  | 위와 같고 어댑터 환경에 `PIP_BREAK_SYSTEM_PACKAGES=1`                       | **번들 Python의 `site-packages`에 설치됐다**(종료 코드 0, 번들 사본에 파일 8개 추가)                                                   |
  | 세대의 venv interpreter + `--extension-manager <번들>/native/bin/aelix`     | 실패한다. 세대는 그대로다                                                                                                              |

  실행 형태만으로는 대화창 설치를 막지 못한다. 사용자 pip 설정 파일과 `--extension-manager`도 같은 경계를
  바꾼다. **[소스]** `uv`를 `PATH`에 둔 실행은 세대에 pip이 있어 pip 경로를 탔다. uv로 넘어가는 경우의
  확인이 아니다.

### 3.4 pip이 하는 접속

| 설정                                                               | 관찰                                                                                                              | 근거 |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ---- |
| native `--offline`만                                               | 빠진 의존성을 PyPI에서 받았다                                                                                     | 실행 |
| `--offline` + `PIP_NO_INDEX=1` + 로컬 `PIP_FIND_LINKS`             | wheel이 직접 URL 의존성(`이름 @ http://…`)을 선언하면 그 URL에서 받았다                                           | 실행 |

overlay가 통과한 `PYTHONUSERBASE` 경로는 `-I`가 그 변수를 무시한다는 문서와 달리 `site.getusersitepackages()`가

권장안의 대화 실행(5.2)은 번들 interpreter에 세대 디렉터리를 더하므로 import 경로만 보면 overlay와 같다.
다른 점은 설치와 장부 관리를 venv 안에서 native CLI가 하고, 대화에서는 `-e`로만 로드해 출처 검사를 거치지
않는다는 것이다.

## 5. 권장 설계

### 5.1 위치와 구성

Studio 사용자 데이터 디렉터리 아래에 둔다. 앱 번들, 사용자의 CLI 환경, CLI와 공유하는 `~/.aelix` 어디에도
쓰지 않는다. 정확한 디렉터리 이름은 구현에서 정한다.

```text
<Studio 사용자 데이터>/aelix-runtime/
  lock                         변경 작업의 프로세스 간 잠금
  current.json                 현재·이전 세대, revision, 묶인 번들, 앱 기본값(직전 사본도 둔다)
  settings.json                확장 설정: 온라인 설치, proxy, 비공개 Git(5.10)
  proxy-credentials-<id>.json  proxy 인증 정보. OS keychain으로 암호화한 것만, 데스크톱 앱에서만(5.10)
  constraints-<lock>.txt       번들에 설치된 배포판과 버전(번들에서 계산)
  artifacts/<묶음>/            파일로 반입한 wheel과 그 sha256 목록
  leases/                      실행 중인 launcher의 lease와 관리형 스냅샷
  generations/<id>/
    venv/                      번들 Python으로 만든 venv. 확장과 추가 의존성만 들어간다
    agent/                     native 설치 기록과 pin (세대와 함께 복제·폐기)
    pack-inputs/               관리형 ACP에 넘기는 pack별 디렉터리
    generation.json            배포판별 이름·버전·RECORD 해시, 확장 entry, 묶인 번들. 이 파일이 있어야 완성된 세대다
```

- 세대는 번들의 경로, `target`, Python minor 버전, `dependencyLockSha256`, native commit에 묶는다(번들
  `manifest.json`에서 읽는다). D04의 "bundled source/ABI/lock에 연결"이 이것이다.
- 앱 기본값은 `current.json`의 선택적 `defaults`에 관리형 확장 ID와 boolean 값으로 적는다. 값이 없는 설치는
  기본으로 켜져 있다. 세대 전환 때 배포판과 entry 이름이 같은 항목의 값을 이어받는다. 모듈과 pack 사이에서
  형태가 달라져도 이 규칙을 적용한다. 이름이 바뀐 entry는 새 항목으로 취급한다. 같은 pack을 여는 entry
  point들은 ID와 기본값을 공유한다. 이름이 그대로인 항목 중 하나라도 명시적으로 꺼져 있으면 pack도 꺼지고,
  이어받을 값이 없으면 기본으로 켜진다.
  기존 ASCII ID 형식은 모듈 `배포판:entry`와 pack `배포판:pack:plugin-id`다. 이 형식이 ACP ID 문법이나 길이 제한에
  맞지 않는 이름에는 배포판과 원래 이름의 SHA-256을 붙인 ASCII ID를 쓴다.
  기본값만 바꾸는 작업은 잠금 아래 현재 포인터를 원자적으로 교체하고 세대와 되돌리기 대상을 유지한다.
- 세대 하나는 약 12MB였다. 거의 전부 세대마다 들어가는 pip이다. **[실행]**

### 5.2 두 가지 실행 형태

|                         | 관리                                                     | 대화                                                                                                                        |
| ----------------------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 쓰는 곳                 | helper의 설치·업데이트·제거·목록·`extension verify`      | ACP가 띄우는 worker, 전환 전 로드 검증                                                                                      |
| interpreter             | `<세대>/venv/bin/python`                                 | 번들의 Python (지금과 같다)                                                                                                 |
| 인자                    | `-I -B -X utf8 <번들>/launch.py native …`                | `-I -S -B -X utf8 <번들>/launch.py`에 세대 `site-packages` 경로를 넘긴다                                                    |
| `site` 모듈             | 켜짐. Python 3.12는 venv 인식을 `site`가 한다            | 꺼짐 (지금과 같다)                                                                                                          |
| `sys.path`              | `native-site`, 표준 라이브러리, 세대 `site-packages`     | `native-site`, 표준 라이브러리, 세대 `site-packages`(launcher가 끝에 추가)                                                  |
| 세대의 코드가 실행될 때 | 시작 코드가 없다는 정적 검사(5.3)를 통과한 세대만 띄운다 | 시작할 때 자동으로 실행되는 것은 없다(`.pth`, `sitecustomize`). `-e`로 넘긴 확장과, 그 뒤 import되는 세대의 모듈이 실행된다 |
| 확장                    | 로드하지 않는다. 설치 장부(entry point)를 읽고 쓴다      | `--no-extensions`와 확장마다 `-e`로 로드한다                                                                                |

대화를 번들 interpreter로 두는 이유다. 모두 실행해 확인했다. **[실행]**

- 세대에 `sitecustomize.py`가 있으면(`.pth`는 하나도 없이) venv interpreter에서는 launcher보다 먼저 실행돼
  세대의 `packaging 23.2`가 쓰였다. `sys.path` 맨 앞이 `native-site`인데도 그랬다. 번들 interpreter에 `-S`로
  세대를 더한 실행에서는 번들의 26.3이 쓰였고 `sitecustomize`도 `.pth`의 코드도 실행되지 않았다.
- 환경에 pip 변수가 없을 때는 대화의 `/extension install`·`remove`가 세대를 바꾸지 못했다. 환경 변수에 따라
  뚫리므로 차단 수단으로 보지 않는다(3.3, 7.3).
- 대화마다 사용자 영역의 실행 파일을 띄우지 않는다. 사용자 영역의 Python은 설치할 때만 쓴다.
- interpreter와 `-I -S -B` 인자가 지금 번들과 같다. 확장을 `--extension`으로 넘기지 않으면 세대의 코드가
  시작할 때 실행되지 않는다. 세대의 디렉터리는 import 경로에 있으므로, 번들에 없는 이름을 누군가 import하면
  세대의 모듈이 쓰인다.
- 수정하지 않은 ACP 어댑터로 확장의 명령과, 세대에만 있는 의존성(`tabulate`)을 쓰는 명령이 실행됐다.

이 형태의 한계다.

- 확장이 `sys.executable`로 자식 Python을 띄우면 그 자식은 세대를 보지 못한다("No module named"). venv
  interpreter로 띄운 worker에서는 보였다. 지금 번들도 같은 제약이 있다(자식이 번들 패키지를 import하지
  못한다). **[실행]**
- 대화의 `/extension list`는 로드된 확장을 "REFUSED (untrusted sys.path provenance)"로 적는다. 장부를 읽는
  명령이 출처 검사를 적용하기 때문이다. 문구를 고치려면 ACP 변경이 필요하다(7.3). **[실행]**
- entry point 경로로는 로드할 수 없다(출처 검사). ACP가 `--no-extensions`를 쓰는 동안은 해당이 없다.

launcher 변경이 필요하다. `launch.py`는 `native-generation` 모드에서 세대 `site-packages` 경로를 인자로 받아
`sys.path` 끝에 더한다. 어댑터와 함께 실행되는 `launch.py acp`가 세대를 고르고 lease를 잡은 뒤 7.4의
확장 인자를 구성한다. host 설정에 저장된 실행 인자에는 세대 경로를 넣지 않는다(D17).
번들 구성 변경이라 다른 작업과 직렬로 한다. **[실행: 처음에는 같은 일을 하는 시험용 launcher로 확인했다.
2026-11-18 launcher 조각에서 번들의 `launch.py`로 구현하고 번들 사본과 실제 어댑터로 대화를 열어 확인했다]**

### 5.3 시작 코드와 번들 이름 정책

정책은 둘이다. 세대의 코드가 interpreter 시작 때 자동으로 실행되지 않는다. 세대가 번들이 가진 이름을
가리거나 보태지 않는다. 대화 실행은 앞의 것을 `-S`로 지킨다. 관리 실행은 `site`를 켜야 하므로, **세대의
interpreter를 띄우기 전에** 파일만 읽는 검사를 한다.

- 세대 `site-packages` 맨 위에 `.pth` 파일, `sitecustomize`, `usercustomize`가 없다.
- `pyvenv.cfg`가 Studio가 쓴 내용과 같다.
- 번들과 같은 이름의 배포판이 없다. 번들과 같은 최상위 모듈·패키지 이름이 없다.

마지막 조건은 필수다. 번들이 항상 이긴다는 것은 import 경로의 순서만으로는 성립하지 않는다. 뒤쪽 경로의
패키지가 앞쪽의 namespace 패키지를 대신하거나 내용을 보탤 수 있다. 그래서 번들과 최상위 이름이 겹치는
패키지는 예외 없이 거부한다. 번들과 namespace를 공유하는 패키지(예: `google.*`)도 거부된다.

검사는 후보를 만든 직후(물려받은 내용)와 설치 도구가 끝난 직후에 한다. 설치 뒤 검사가 실패하면 후보의
interpreter를 다시 띄우지 않고 지운다. `sitecustomize.py`를 싣는 wheel, `.pth`를 싣는 wheel, `packaging/`을
싣는 wheel이 모두 설치 뒤 검사에서 걸려 전환되지 않았다. **[실행]**

### 5.4 설치·업데이트·제거 절차

1. 파일 반입이면 정적 검사(5.9)를 하고, 통과한 wheel 묶음을 `artifacts/`에 복사한다. 설치는 그 사본으로 한다.
2. 잠금을 잡는다. 완성되지 않은 후보를 지우고 현재 포인터와 revision을 읽는다(5.6).
3. 후보를 만든다. 번들 Python으로 새 venv를 만들고(오프라인, 복사까지 약 2초), 부모 세대의 `RECORD`에 적힌
   파일을 전부 복사한다. console script와 `site-packages` 밖의 data 파일이 포함된다. 스크립트 첫 줄의
   interpreter 경로를 후보의 것으로 고친다. `agent/`를 복사한다.
4. 정적 검사(5.3)를 한다.
5. 후보에서 native CLI를 관리 형태로 실행한다: `--offline`(반입일 때) `extension install|update|remove <대상> --yes`.
6. 종료 코드가 0이나 3이 아니면 후보를 지운다. 3(설치됐지만 manifest가 묶이지 않음)은 그 확장의 상태를
   "manifest 미결합"으로 기록하고 다음 단계로 넘긴다(8.2의 A2, 5.11의 `list` 상태).
7. 정적 검사를 다시 한다. 실패하면 후보를 지운다.
8. 요청과 결과를 대조하고 로드를 검증한다(5.5). 하나라도 실패하면 후보를 지운다.
9. `generation.json`을 쓰고, revision이 2번에서 읽은 값과 같은지 확인한 뒤 `current.json`을 임시 파일에
   쓰고 rename으로 바꾼다.

1a helper는 설치 요청에서 파일, 이름(선택적으로 고정 버전과 index), git URL(선택적으로 빌드 의존성 index)을
받는다. 이름과 git은 파일 반입과 같은 후보·검증·전환 절차를 따른다. 이름 설치는 정규화한 배포판 이름과
요청한 버전을 대조한다. git 설치는 변경된 확장 배포판의 `direct_url.json`에서 요청 URL과 실제 commit을
대조한다. 이름·git으로 설치한 wheel 사본은 보관하지 않는다(A11). 기존 파일 업데이트·제거 요청은 유지한다.

1차 실험의 후보 복제는 `site-packages`만 복사했다. 그 방식으로는 다음 설치 뒤에 console script와 data
파일이 사라졌다. `RECORD` 기준 복사로 바꾸니 남았고 스크립트가 새 세대의 interpreter로 실행됐다. **[실행]**

native CLI와 로드 검증에 넘기는 환경은 Studio가 **허용 목록으로** 새로 만든다. `PATH`, `HOME`, 임시
디렉터리, locale처럼 정한 변수만 넘기고 나머지는 넘기지 않는다. 사용자 환경의 `PYTHON*`, `PIP_*`, `UV_*`,
`VIRTUAL_ENV`, proxy 변수, 그리고 native가 경로를 바꾸는 데 쓰는 변수가 여기서 빠진다:
`AELIX_SETTINGS_PATH`, `AELIX_AUTH_PATH`, `AELIX_CODING_AGENT_DIR`, `AELIX_CODING_AGENT_SESSION_DIR`,
`AELIX_MCP_CONFIG`, `AELIX_PROJECT_DIR`, `AELIX_DEFAULT_CATALOG`, `AELIX_MODEL_CATALOG_URL`, `XDG_CONFIG_HOME`
(pin의 소스에서 찾은 이름이다).
후보의 agent dir만 주고 `AELIX_SETTINGS_PATH`를 남겨 두면 설치 기록이 후보 밖의 그 파일에 쓰였다. 허용
목록으로 바꾸니 밖에는 아무것도 쓰이지 않았다. **[실행]**

아래는 Studio가 넣는 변수다. 부모(`-I`)는 `PYTHON*`을 무시하고 pip 자식만 읽는다. **[실행]**

| 환경 변수                             | 이유                                                                                                                                                                                                                                                                                                     |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AELIX_CODING_AGENT_DIR=<세대>/agent` | native가 설치 기록을 CLI와 공유하는 `~/.aelix/agent/settings.json`에 쓰지 않게 한다. 버린 후보의 기록도 함께 사라진다                                                                                                                                                                                    |
| `PYTHONPATH=<번들>/native-site`       | pip이 번들에 이미 있는 패키지를 설치된 것으로 본다. 없으면 pip은 번들에 무엇이 있는지 모른다                                                                                                                                                                                                             |
| `PIP_CONSTRAINT=<constraints URL>`    | 번들과 다른 버전을 요구하는 확장을 설치 단계에서 실패시킨다. 없으면 pip이 다른 버전을 세대에 깔고, 실행 때는 번들 버전이 조용히 이긴다                                                                                                                                                                   |

| `PYTHONDONTWRITEBYTECODE=1`           | 번들 표준 라이브러리에 `.pyc`가 생기지 않게 한다(3.2). main의 launcher에서는 Studio가 주지 않으면 번들이 바뀐다                                                                                                                                                                                          |
| `PIP_DISABLE_PIP_VERSION_CHECK=1`     | pip이 스스로 PyPI에 버전을 묻지 않게 한다                                                                                                                                                                                                                                                                |
| `PIP_NO_INPUT=1`                      | pip이 입력을 기다리며 멈추지 않게 한다                                                                                                                                                                                                                                                                   |
| 오프라인 반입일 때                    | `PIP_NO_INDEX=1`, `PIP_FIND_LINKS=<보관소 URL>`, 죽은 proxy(5.9)                                                                                                                                                                                                                                         |
| `PIP_INDEX_URL`                       | `update`에는 `--index-url`이 없어 이 변수로 내부 index를 준다                                                                                                                                                                                                                                            |
| 온라인 설치에 사용자 proxy가 있을 때  | `PIP_PROXY`, `http_proxy`·`https_proxy`(대문자 포함), 빈 `no_proxy`, Git `http.proxy`. proxy가 인증을 요구하면 이 주소는 그 변경의 loopback relay(`http://run:<token>@127.0.0.1:<port>`)이고, Git에는 relay 주소의 credential helper를 비우는 항목을 더한다. 없으면 `no_proxy=*`와 빈 `http.proxy`(5.10) |

| 온라인 설치의 Git 전송 정책           | `protocol.*.allow`: 요청 저장소는 받은 scheme, submodule은 HTTPS만(비공개 Git이면 SSH도)(5.10)                                                                                                                                                                                                           |

`PIP_CONSTRAINT`와 `PIP_FIND_LINKS`는 공백으로 값을 나눈다. "Application Support"처럼 공백이 있는 경로는
깨졌고, `file://` URL로 주니 공백과 한글 경로에서 동작했다. **[실행]**

#### 5.4.1 설치한 온라인 출처에서 최신으로 올리기 (1b, PR C)

사용자가 `upgrade`를 요청하면 잠금 아래에서 현재 세대의 출처와 온라인 설정을 읽는다.
이름 설치의 `origin.requirement`에는 입력한 패키지 이름과 PEP 440 버전 제약을 원문 그대로 저장한다.
기존 `name`과 `version` 필드는 `name==version`으로 기록한다. 저장된 단일 index와 requirement를
다시 사용하며, 버전 범위 안에서 pip이 선택한 최신 호환 버전을 적용한다. `==1.2.*`는 범위이고,
정확한 `==` 또는 `===` 절은 `PINNED`로 거절한다. 사용자는 다른 버전으로 다시 설치할 수 있다.
requirement 필드가 없던 개발·시험 세대는 `PIN_UNKNOWN`으로 답한다. 사용자가 명시적으로 확인해
`allowUnpin: true`를 보내면 이름만으로 해석하고, 전환에 성공한 세대부터 그 이름을 requirement로 남긴다.

- 잠금 아래에서 네트워크와 proxy 인증보다 먼저 출처를 대조한다. 같은 OS 사용자가 Studio 데이터에
  쓸 수 있으면 활성 세대 코드도 바꿀 수 있으므로, 이 검사는 저장 기록 사이의 불일치를 찾는다.
  Git은 설치된 PEP 610 `direct_url.json`의 정규화한 저장소 URL·commit·하위 경로와 대조한다. 하위 경로
  설치 시 검증된 staging 출처를 VCS 형식으로 남긴다. 예전 하위 경로 설치에 임시 경로만 남았으면
  `UPGRADE_SOURCE_MISMATCH`로 안내하고 재설치로 출처를 갱신한다.
- 이름 출처는 설치된 배포판 이름과 버전이 requirement에 맞는지 확인한다. Studio 설정에는 index
  허용 목록이 없다. 새 설치의 배포판에 남긴 index·requirement와 세대 기록을 대조한다. 이 메타데이터가
  없는 이전 설치의 index는 URL 형식과 기존 온라인 설치 정책만 확인할 수 있다. `RECORD`에 사본이
  있는데 파일이 없거나 index 출처에 PEP 610 직접 출처가 남아 있으면 `UPGRADE_SOURCE_MISMATCH`다.
- 이름 출처는 잠금 아래의 임시 venv와 번들 pip로 저장된 index에서 조회한다. 설치된 패키지를 무시하므로
  index 접속 실패가 "이미 최신"으로 처리되지 않는다. 조회에서 선택한 파일의 URL과 강한 hash로 후보를
  설치한다. 같은 버전의 파일이 교체되거나 yank돼도 조회에서 얻은 파일만 시도한다. 다운로드 URL은 pip에
  전용 표준 입력으로 넘기고, 진단 출력의 URL에서 query와 fragment를 가린다.
  업그레이드 pip의 Simple API 응답은 압축을 푼 뒤 8 MiB, `resolution.json`은 1 MiB까지 받는다.
  조회와 보고서 읽기·해석에 같은 시간 제한을 적용한다. 상한을 넘기면 `UPGRADE_RESPONSE_TOO_LARGE`다.
- Git은 원래 URL의 ref를 다시 해석한다. 저장한 commit과 같은 길이의 full SHA ref는 `PINNED`다.
  일반 Git은 후보에서 해당 배포판만 제거하고 같은 ref를 설치한다. 실제 pip에서 Git의 `--upgrade`는
  배포판 버전이 같으면 commit이 움직여도 다시 설치하지 않았다. 다시 설치한 배포판과 PEP 610의 commit이
  각각 원래 배포판과 사전 확인한 commit에 맞아야 한다. 그 사이 ref가 또 움직이면 후보를 거절한다.
- Git 하위 경로는 먼저 commit을 비교한다. commit이 바뀌면 설치와 같은 경로 및 submodule 검사·staging 사본을 사용한다. 로컬 디렉터리
  설치는 배포판 버전이 같아도 pip이 다시 설치한다. 사본의 설치 기록과 체크아웃 commit을 검증한다.
- index가 새 버전을 고르지 않거나 Git commit이 같으면 `already_latest`로 끝낸다. 임시 파일은 잠금
  holder가 지우고 새 세대나 포인터 전환은 없다. 변경이 있으면 5.5의 검증을 통과한 후보만 전환한다.
  파일 출처의 새 wheel 반입은 기존 오프라인 `update`를 사용한다.

### 5.5 전환 전 검증

전환 전에 후보의 모든 배포판에서 `RECORD`가 가리키는 파일이 실제로 후보 안에 있는지 확인한다.
`RECORD`에 hash가 있으면 파일 내용도 대조한다. 마지막 로드 검사 뒤에 같은 `RECORD`와 파일을
포인터 전환 직전에 다시 확인한다. 스크립트 실행 경로를 새 세대에 맞게 다시 쓰면
같은 변경에서 hash를 갱신한다. 세대 복사에서 제외하는 bytecode cache는 해당 `RECORD` 행도 정리한다.
Git 업그레이드 대상과 다른 배포판이 파일을 같이 기록하면 `SHARED_DISTRIBUTION_FILES`로 거절한다.

| 검사                                                                                                                                                               | 잡는 것                                                                   | 실행한 실패 예                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 정적 검사(5.3)                                                                                                                                                     | 시작 코드, 번들과 겹치는 배포판·모듈                                      | `sitecustomize.py`, `.pth`, `packaging/`을 싣는 wheel. constraints 없이 설치해 `packaging 23.2`가 깔린 경우                |
| native 종료 코드 0                                                                                                                                                 | 설치 도구 실패                                                            | 번들과 충돌하는 의존성(`packaging<24`, 번들 26.3): pip `ResolutionImpossible`, 종료 코드 1                                 |
| **요청 대조.** 설치 전후의 배포판(이름·버전·`RECORD` 해시)과 확장 entry point를 비교해 기대 확장 집합을 만든다                                                     | 요청한 것이 설치되지 않았거나, 확장이 아니거나, 다른 것이 사라지거나 바뀜 | entry point가 없는 wheel: native 종료 0, 대조가 없던 2차 검증은 빈 목록으로 통과해 전환까지 됐다. 대조를 넣은 뒤 거부됐다  |
| **로드 검사.** 대화 형태로 native를 띄운다: `--mode rpc --offline --no-session --no-extensions`와 기대 집합의 확장마다 `-e <모듈 참조>`. `resources/list`를 읽는다 | 기대 집합의 모든 확장이 `extensions`에 있고 `extensionErrors`가 비었다    | import가 깨진 pack, `setup()`이 예외를 내는 pack. 둘 다 지연 활성화 pack이었고 native 설치는 0, `status`는 오류 없음이었다 |
| manifest가 결합되는 형태로 넘길 때(8.2의 A2) 그 인자로 한 번 더                                                                                                    | `extensionErrors`에 나오는 로드 오류                                      | 실행한 실패 예 없음                                                                                                        |
| `aelix extension verify`                                                                                                                                           | manifest 결합 상태. 화면에 보일 상태로 기록한다                           | —                                                                                                                          |

**기대 확장 집합은 선택이 아니라 필수다.** 요청마다 다음을 확인한다.

| 요청          | 확인                                                                                                                                                                                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 설치·업데이트 | 요청한 배포판이 후보에 있다(파일이면 wheel의 이름·버전과 같다). 그 배포판에 `aelix.extensions` entry point가 하나 이상 있다. 전에 있던 배포판이 사라지지 않았다. 바뀌지 않은 배포판의 확장이 그대로 있다         |
| 업데이트      | 위에 더해, 배포판이 하나도 바뀌지 않았으면 "변경 없음"으로 끝내고 전환하지 않는다                                                                                                                                |
| 제거          | 대상 배포판과 그 확장이 후보에 없다. 다른 배포판은 버전과 `RECORD` 해시가 그대로다. 기대 집합은 전의 집합에서 대상의 확장을 뺀 것이다. 마지막 확장을 제거하면 기대 집합이 빈 집합이고, 이때만 빈 집합이 통과한다 |
| 번들 교체     | 기대 집합은 옮기기 전 세대의 집합이다                                                                                                                                                                            |

git 주소처럼 배포판 이름을 미리 알 수 없는 설치는 변경된 확장 배포판 중 요청한 git URL과 일치하는 설치
기록이 하나일 때만 대상을 정한다. 전체 commit을 요청했다면 설치 기록의 commit도 같아야 한다. 이 대조를 넣은 절차로 파일·이름·git 설치, 업데이트, "변경 없음", 제거, 마지막
확장 제거, 번들 교체 뒤 옮기기와 되돌리기를 실행했다. 기록을 다시 설치하는 재구축은 대조를 넣은 뒤로는
실행하지 않았다. **[실행]**

- 로드 검사를 `-e <모듈 참조>`로 하는 이유: 이 경로는 지연 활성화가 없어 import와 `setup()`이 그 자리에서
  실행된다. 깨진 pack 두 종류(import 실패, `setup()` 실패)에서 `status --json`은 둘 다 통과했고, entry
  point를 직접 import하는 검사는 `setup()` 실패를 놓쳤고, 이 검사만 둘 다 잡았다. **[실행]**
- 로드 검사가 보는 것은 `resources/list`의 `extensionErrors`다. manifest가 선언한 MCP 서버의 capability
  거부나 접속 실패는 native가 시작할 때 따로 처리하고 경고로만 남길 수 있다. 이 검사로 잡는다고 보지
  않는다. **[소스]**
- 로드 검사에는 후보의 `agent/`를 agent dir로 준다. 대화와 같은 agent dir을 주면 native가
  `~/.aelix/agent/auth.json`을 만든다. **[실행]**
- 관리형 스냅샷 검사는 기본값이 꺼진 항목을 포함한 전체 후보 목록을 검사한다. 모듈에는 ACP 관리형 로더의
  출처 검사 코드를 번들 native 환경에서 실행한다. 현재 pin에서는 [ACP #38](https://github.com/handochan/aelix-acp/pull/38)의
  검사 파일을 별도 동봉한다. pack은 하나의 설치 패키지를 가리키는 전용 디렉터리로 구성하고 native 로드 검사에
  그 디렉터리를 넘긴다. 관리형 입력이나 모듈 출처 검사에 실패하면 `MANAGED_EXTENSION_INVALID`로 거절한다.
- 검증은 확장의 `setup()`을 실행한다. 사용자가 설치를 승인한 코드다. 그 코드가 하는 접속은 막지 못한다(5.9).
  확장의 명령을 실제로 실행해 보지는 않는다. 명령 안에서 나는 오류는 잡지 못한다.
- entry point 경로에서 지연 활성화 pack을 명령 실행 없이 확인하는 방법은 native에 없다(7.2). 대화가 그
  경로를 쓰지 않는 동안은 필요하지 않다.

### 5.6 동시 실행, 중단, 정리

- **잠금.** 설치·업데이트·제거·되돌리기·번들 교체 처리·정리는 `lock` 파일의 OS 잠금을 잡고 한다. 두
  프로세스가 동시에 설치를 시작하니 둘째가 8초 기다린 뒤 첫째의 결과 위에 설치했고 두 확장이 모두 남았다.
  **[실행: macOS의 `flock`. Windows의 잠금은 확인하지 않았다]**
- **revision.** 포인터에 revision을 둔다. 전환 직전에 다시 읽어 후보를 만들 때의 값과 다르면 전환하지
  않는다. 잠금이 기대대로 동작하지 않는 파일 시스템을 위한 이중 확인이다. **[실행: 값이 올라가는 것만]**
- **중단된 후보.** `generation.json`이 없는 세대 디렉터리는 완성되지 않은 후보다. 다음 변경 작업이 잠금을
  잡은 뒤 지운다. **[실행]**
- **포인터.** 임시 파일에 쓰고 디스크에 내린 뒤 rename한다. 직전 포인터의 사본을 남긴다. 포인터를 읽을 수
  없거나 가리키는 세대가 완성되지 않았으면 직전 사본을 쓰고, 그것도 안 되면 번들만으로 시작한다. 잘린
  포인터로 시험하니 직전 사본으로 시작했다. 마지막 전환 한 번이 빠진 상태가 된다. **[실행]**
- **실행 중인 세대의 보호.** launcher는 고른 세대에 lease 파일을 만들고 프로세스가 끝날 때까지 잠금을 잡는다.
  정리는 현재·이전 세대와 lease 잠금이 살아 있는 세대를 지우지 않는다. lease를 잡은 프로세스가 있는 동안 그
  세대는 남았고, 끝난 뒤 정리에서 지워졌다. **[실행]**
- **lease를 잡는 순서.** launcher는 변경 잠금을 잡은 채로 포인터를 읽고 그 세대의 lease를 잡은 뒤 변경 잠금을
  놓는다. 포인터를 읽는 것과 lease를 잡는 것 사이에 전환이나 정리가 끼어들지 못한다. **[실행: launcher 조각]**
- **잠금 없는 lease.** 설치는 변경 내내 잠금을 쥔다. launcher가 그만큼 기다리면 그동안 연 대화가 수 분
  멈추므로, 2초 기다린 뒤에는 잠금 없이 lease를 잡는다. 이 경로는 세 가지에 기대어 성립한다. 정리는 잠금
  아래에서, 그 변경의 전환 뒤에 돈다. 현재·이전 세대에서 한 번 빠진 세대는 다시 들어오지 않는다(새 세대는 새
  이름을 받고, 되돌리기는 이전 세대만 현재로 올린다). launcher는 lease를 잡은 뒤 포인터를 다시 읽어, 고른
  세대가 여전히 현재나 이전일 때만 쓰고 아니면 다시 고른다. lease는 세대 이름이 없는 임시 이름(`.pending.…`)으로
  만들어 잠근 뒤에야 세대 이름으로 rename한다. 정리가 지우는 것은 잠기지 않은 채 본 lease뿐이므로, 세대 이름을
  단 lease가 정리에 지워지는 일은 없다. 정리가 임시 파일을 먼저 지웠으면 rename이 실패하고 다시 잡는다.
  **[실행: launcher 조각. 생성과 잠금 사이에 정리를 끼워 넣는 harness로 고치기 전의 결함과 고친 뒤를 확인했다.
  실제 경합 빈도는 보지 않았다]**
- **lease 반납.** 어댑터가 정상으로 끝나면 lease 파일을 지운 뒤 잠금을 놓는다. 비정상 종료가 남긴 lease는
  잠기지 않으므로 다음 정리가 지운다. **[실행]**
- **전환 뒤의 실패.** 포인터 rename이 된 뒤 디렉터리를 디스크에 내리는 단계가 실패하면 그 변경은 실패로
  보고되지만 후보는 이미 현재 세대다. helper는 후보를 지우기 전에 포인터를 다시 읽어, 현재나 이전으로
  적힌 후보는 지우지 않는다. 잠금 없는 launcher가 그 세대를 이미 골랐을 수 있기 때문이다. **[실행: 단위 시험]**
- **되돌리기와 번들 교체 처리.** 잠금을 잡은 뒤에 포인터를 읽는다. 잠금 밖에서 읽은 포인터로 전환하지
  않는다. **[추정: 설계]**
- **시험 스크립트의 차이.** 시험 스크립트의 되돌리기는 포인터를 읽은 뒤 잠금을 잡고, lease도 세대를 고른
  뒤에 잡는다. 위 두 항목의 순서는 실행으로 확인한 것이 아니다.
- **반입 보관소.** 어느 세대의 기록도 가리키지 않는 묶음은 정리에서 지운다. **[추정: 구현하지 않았다]**
- 실행 중인 어댑터는 시작할 때의 세대를 계속 쓴다. 새 세대는 다음 어댑터 시작부터 적용한다. 새 대화와,
  유휴 정리나 런타임 재시작 뒤 어댑터가 다시 뜬 기존 대화가 그 시점의 현재 세대를 쓴다(8.2의 A2 보완 결정).
  목록의 `appliesAt`은 `next_adapter_start`다.

### 5.7 되돌리기

- 실패한 작업은 전환 자체를 하지 않으므로 되돌릴 것이 없다. **[실행]**
- 사용자가 직전 상태로 되돌릴 때, 이전 세대가 지금 번들에 묶여 있으면 포인터만 바꾼다. 다른 번들에 묶여
  있으면 5.8과 같이 그 내용을 새 후보로 옮겨 검증한 뒤 전환한다. **[실행]**
- 되돌리기는 직전 한 단계다(8.2의 A12).

### 5.8 Studio 업데이트 (G16)

세대는 앱 밖에 있어 번들을 교체해도 파일은 남는다. launcher는 시작할 때 세대가 묶인 번들 정보와 지금
번들을 비교한다. 다르면 그 세대를 쓰지 않고 번들만으로 시작하며, helper가 아래를 한다. **기존 세대는
고치지 않는다.** 1차 실험은 현재 세대의 링크를 먼저 고친 뒤 검증했는데, 검증이 실패하면 고친 상태로 남는
결함이 있었다.

| 새 번들                                 | 처리                                                                                                          | 확인                                                                                                             |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 같은 Python minor                       | 새 번들의 Python으로 후보 venv를 만들고 현재 세대의 내용을 복사한다. 5.3–5.5를 거쳐 전환한다                  | 실행. 옛 번들을 지운 뒤에도 내용을 옮겨 전환했다. 옛 세대의 링크는 지워진 번들을 가리킨 채 그대로였다            |
| 위 검증이 실패(새 lock과 겹치거나 빠짐) | 빈 후보에 설치 기록을 순서대로 다시 설치하고 검증·전환한다                                                    | 실행(모의). 번들이 `tabulate`를 싣게 된 경우와 빼게 된 경우. 보관소의 wheel로 네트워크를 전부 막고 다시 만들었다 |
| Python minor가 다르다                   | 설치된 파일을 재사용할 수 없다. 설치 기록으로 다시 만든다. 컴파일된 모듈이 든 wheel은 새 버전용이 있어야 한다 | 1차에서 감지만 실행. 3.13 번들이 없어 다시 만들기는 실행하지 않았다                                              |

1a helper의 `reconcile_bundle` 요청은 포인터를 잠금 아래 다시 읽고, target과 Python minor가 맞으면 새
venv로 복사한다. 배포판 기록·확장 집합·의존성과 로드 검사를 통과한 경우에만 전환한다. 복사할 수 없거나
검증이 실패하면 원본 해시를 확인한 보관 wheel로 재구축을 시도한다. 이름·git 출처를 다시 받으려면 사용자의
설치 요청이 필요하다. 번들 교체만으로 index나 git에 접속하지 않는다. 이 요청을 호출하는 Studio 연결은
1b에서 한다. launcher는 검증된 새 세대가 선택되기 전까지 번들만으로 시작한다.

옮기기와 재구축이 실패하면 후보를 정리하고 포인터와 옛 세대를 보존한다. helper는 저장된 번들 바인딩을
비교해 목록에 `reinstall_needed`를 반환한다. 사용자가 빈 세대부터 다시 설치하기로 확인하면
`replaceIncompatible: true`로 설치를 요청할 수 있다. 성공한 뒤에만 전환하고 기존 상태는 직전 세대로 보존한다.

다시 만들 때 쓸 수 있는 것을 정의한다.

| 설치 방식   | 남는 것                                                                      | 다시 만들기                                               |
| ----------- | ---------------------------------------------------------------------------- | --------------------------------------------------------- |
| 파일 반입   | 반입한 wheel과 같은 폴더의 의존 wheel 전부의 사본, 파일별 sha256             | 오프라인으로 가능. 같은 바이트를 다시 설치한다 **[실행]** |
| 이름(index) | 이름, 설치된 버전, 배포판의 `RECORD` 해시, index 주소. **wheel 사본은 없다** | index에 다시 접속해야 한다. 같은 버전을 지정할 수 있다    |
| git         | 주소, 설치된 commit, 빌드 도구 index                                         | git 주소와 빌드 도구 index에 다시 접속해야 한다           |

- 이름·git 설치도 wheel 사본을 남기려면 Studio가 `pip download`를 직접 실행해 받은 뒤 그 사본으로 설치해야
  한다. `aelix extension`만 쓴다는 규칙의 예외다. 보관하지 않기로 정해졌다(8.2의 A11). 사본이 있어도 새
  Python·ABI와 새 번들의 의존성에 맞을 때만 다시 만들 수 있다.
- 옮기기도 다시 만들기도 실패하면 launcher는 번들만으로 시작한다. 이것이 실행해 본 동작이다. 맞는 확장만
  남기는 것은 공유 의존성을 다시 구성하고 검증하는 설계가 따로 필요하다. 어느 쪽으로 낼지는 G16에 닿으므로
  사용자 결정이고, 확장 없이 시작하고 안내하는 쪽으로 정해졌다(8.2의 A4).
- 이전 세대는 옛 번들에 묶여 있어 그대로는 실행할 수 없다. 되돌릴 때 내용을 옮긴다(5.7).
- CLI와 공유하는 `~/.aelix`는 이 과정에서 쓰지 않는다. G16의 "공유 원본은 보존"과 맞는다.

### 5.9 오프라인 wheel 반입 (G12)

native의 `--offline`과 pip 환경 변수만으로는 접속을 막지 못한다(3.4). 접속하는 주체가 둘이라 따로 적는다.

**설치 도구(native CLI와 pip).** 다음을 함께 쓴다.

1. **설치 도구를 실행하기 전의 정적 검사.** 반입 묶음의 파일을 읽기만 한다.
   - wheel만 받는다. 소스 묶음은 빌드 코드를 실행하고 빌드 도구를 받으려 한다.
   - 어느 wheel이든 직접 참조 의존성이 있으면 거부한다. `METADATA`를 헤더로 읽고 `Requires-Dist`를 PEP 508로
     해석해 판단한다. 이미 후보에 복사된 배포판도 같은 조건을 확인한다. 문자열 검색으로는 안 된다. " @ "를 찾던 검사는 `이름@git+ssh://…`를 통과시켰고, pip이
     `git clone`을 실행했다. 해석 방식으로 바꾸니 설치 도구를 실행하기 전에 거부됐다. **[실행]**
2. 통과한 묶음을 보관소에 복사하고 그 사본으로 설치한다. `--offline`, `PIP_NO_INDEX=1`,
   `PIP_FIND_LINKS=<보관소>`, pip 설정 파일 무시, 허용 목록 환경(5.4).
3. 보조 장치로 죽은 proxy를 설치 도구 환경에 준다. HTTP(S) 요청만 막는다. git·ssh는 막지 못한다.
   사용자가 확장 설정에 proxy를 입력했거나 비공개 Git을 켜도 파일 반입에는 넣지 않는다. 오프라인 반입과
   온라인 설정을 한 환경에 함께 넣으려 하면 환경을 만들지 않고 오류로 끝난다. **[실행: 단위 시험]**

**설치한 확장의 코드.** 전환 전 로드 검증은 확장의 `setup()`을 실행하고, 대화도 확장을 실행한다. `setup()`이
HTTP 요청을 하는 pack을 오프라인 설정으로 반입하니 로드 검증 중에 요청이 나갔다. **이것을 막는 장치는 지금
없다.** 만들려면 프로세스의 네트워크를 OS 수준에서 막아야 하고, 이 문서는 그것을 설계하지 않는다. 폐쇄망에서
"반입 절차가 접속하지 않는다"는 말은 설치 도구까지다. 반입하는 확장이 접속하지 않는다는 것은 Studio가
보장하지 못한다. **[실행]**

각 실험이 무엇의 증거인지 구분한다.

| 실험                                                                                                   | 증거가 되는 것                                                                                                  | 증거가 되지 않는 것                                        |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| macOS sandbox로 네트워크를 전부 막고 반입(의존성 없음, 의존성이 폴더에 있음, 번들 교체 뒤 다시 만들기) | 막힌 환경에서 절차가 끝까지 성공한다                                                                            | 접속을 시도하지 않는다는 것                                |
| 직접 참조 의존성이 있는 wheel                                                                          | 정적 검사가 설치 도구를 실행하기 전에 거부한다. 검사 없이 같은 설정이면 접속을 시도한다                         | 검사가 모든 형태의 참조를 잡는다는 것                      |
| Python 소켓 호출 추적(audit hook): native 부모, pip 자식, `extension verify`, 로드 검사                | 접속하지 않는 확장을 반입한 이 실행에서 연결·이름 조회·전송 호출이 없었다. `urllib3`의 `::1` bind 확인만 있었다 | 다른 OS, 다른 패키지, Python 밖의 코드(컴파일된 모듈, git) |
| sandbox가 system log에 남긴 거부 기록                                                                  | curl과 pip의 연결 시도가 기록된다                                                                               | 횟수. `urllib3`의 bind 시도 일부가 기록되지 않았다         |

출시 후보의 외부 접속 감사(Studio #15)에 "오프라인 반입" 시나리오를 넣어야 한다. 아직 실행하지 않았다. 그
감사는 실행한 시나리오와 그때 쓴 확장에 대한 증거다. `urllib3`의 loopback bind는 그 감사에서 따로 분류해야
할 수 있다. **[추정]**

의존성이 없는데 폴더에도 없는 wheel은 약 2초 만에 종료 코드 1로 끝났고 현재 세대는 그대로였다. venv
만들기는 번들 Python에 든 pip wheel을 써서 오프라인이다. **[실행]**

### 5.10 외부 접속: 보장하는 것과 하지 않는 것

| 상황                               | 접속                                                                                                                                                                                                                  | 근거                                                     |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 확장 화면 열기, 목록 보기          | 하지 않는다. helper는 파일을 읽고 `extension list`·`verify`만 실행한다                                                                                                                                                | `verify` 추적은 실행. 화면은 아직 없다                   |
| 파일 반입                          | 설치 도구는 하지 않도록 만든다. 반입한 확장의 코드가 로드 검증 중에 하는 접속은 막지 못한다(5.9)                                                                                                                      | 5.9                                                      |
| 이름으로 설치                      | 사용자가 실행할 때만. **접속 대상은 지정한 index로 한정되지 않는다.** index가 가리키는 파일 host, 패키지가 선언한 직접 URL, 소스 패키지면 빌드 도구를 받는 곳과 빌드 코드까지다                                       | 직접 URL은 실행. 나머지는 pip 동작 [추정]                |

- helper 설정 `onlineInstallEnabled`는 기본 켜짐이다. 끄면 이름과 git 요청을 자식 프로세스를 띄우기
  전에 `ONLINE_INSTALL_DISABLED`로 거절한다. 파일 반입은 계속 쓸 수 있다. 확장 코드의 로드 검증에는
  5.9의 범위가 적용된다.
- 이름과 git의 pip 기본 index는 공개 PyPI(`https://pypi.org/simple/`)다. 공식 index의 wheel은
  `files.pythonhosted.org`에서 받을 수 있다. 내부 index를 지정하면 그 index를 쓰며 Studio는 추가 index를
  설정하지 않는다. git 주소, index의 파일 주소와 redirect, 패키지가 선언한 직접 URL 및 빌드 의존성·코드의
  접속은 위 표와 같은 범위다.
- 온라인 `upgrade`는 명시적으로 요청할 때만 기존 출처를 다시 확인한다. 설정이 꺼지면 이름·Git 설치와
  함께 `ONLINE_INSTALL_DISABLED`로 거절한다. 조회나 목록을 표시할 때는 확인 요청을 보내지 않는다.
  사용자의 proxy·private Git 설정은 설치와 같다. 인증이 필요한 경우 확인과 설치가 그 작업의 loopback
  relay 하나를 사용하고, 작업이 끝나면 닫는다.
  Git의 임시 clone과 checkout에는 Studio의 고정 reflog 작성자 정보를 준다. Git이 기본 이메일을 만들려고
  시스템 hostname을 DNS에 조회하는 것을 막는다.
- 온라인 설치 도구에는 후보 전용 홈·임시 디렉터리와 시스템 실행 경로를 준다. pip와 Git의 사용자·시스템
  설정, 환경·시스템 프록시, netrc·credential helper·SSH 사용자 설정·키는 적용하지 않는다. 예외는 사용자가
  Studio 확장 설정에서 직접 정한 두 가지뿐이다(아래의 proxy와 비공개 Git). SSH는 기존 known-hosts 파일로
  호스트를 검증한다. 로드 검증과 패키지의 빌드 코드는 별도의 네트워크 격리 경계 밖이다.
- **확장 설정.** `<Studio 사용자 데이터>/aelix-runtime/settings.json`에 온라인 설치 켜짐(기본 켜짐), proxy(기본
  없음), 비공개 Git(기본 꺼짐)을 둔다. 저장은 포인터와 같이 변경 잠금 아래에서 임시 파일에 쓰고 디스크에
  내린 뒤 잠금 보유 프로세스가 rename한다. 변경 작업은 잠금을 잡은 뒤 설정을 한 번 읽고 끝까지 그 값을
  쓴다. 설정 저장도 변경이라 다른 변경이 도는 동안에는 `BUSY`다. 파일을 읽을 수 없으면 닫힌 값(온라인 설치
  꺼짐, proxy 없음, 비공개 Git 꺼짐)을 적용하고 `SETTINGS_UNREADABLE`로 알린다. 다시 저장하면 풀린다.
  Studio 정책 옵션(`onlineInstallEnabled: false`)은 설정보다 위에서 온라인 설치를 끈다. 그 이름에 일반 파일이
  아닌 것(링크, 대상이 없는 링크 포함, 디렉터리)이 있으면 읽을 수 없는 것으로 본다. 읽기도 링크를 따라가지
  않는다. **[실행: 단위 시험, 번들 lock holder]**
- **proxy.** [2026-11-19 Issue #32 결정](https://github.com/handochan/aelix-studio/issues/32#issuecomment-7011959904)대로
  사용자가 입력한 주소만 쓴다. `http://` 또는 `https://`의 host와 선택적 port(1–65535)만 받아 정규화해
  저장한다. 입력한 그대로의 authority를 먼저 검사하고 고쳐 받지 않는다. scheme 뒤의 빗금이 더 있는 주소
  (`http:///user:pass@host`처럼 URL 해석이 인증 정보를 조용히 버리는 것)와 port 0은 `INVALID_PROXY`다.
  이름·git 설치 도구에 pip `--proxy`(`PIP_PROXY`, pip이 환경 proxy와 netrc를 읽지 않게 된다), 표준
  `http_proxy`·`https_proxy`(대문자 포함), 빈 `no_proxy`, Git `http.proxy`로 넘긴다. pip의 index·파일 host·직접
  URL·빌드 의존성 설치(자식 pip이 환경을 물려받는다), HTTPS Git(pip의 clone과 Studio의 하위 경로 fetch)이
  이 proxy를 거친다. 입력하지 않으면 `no_proxy=*`와 빈 `http.proxy`로 시스템·환경 proxy를 쓰지 않는다.
  **덮지 못하는 것:** SSH Git(`ssh://`, `git@host:`)과 `git://`은 HTTP proxy를 쓰지 않는다(비공개 Git을 켜면
  사용자 SSH 설정의 `ProxyCommand`·`ProxyJump`가 적용된다). 로드 검증과 대화의 확장 코드, 표준 변수를
  무시하는 빌드 코드도 덮지 못한다. 파일 반입은 proxy 설정과 무관하게 죽은 proxy를 유지한다(5.9).
  **[실행: 번들 pip과 native로 loopback proxy를 거친 이름 설치, 시스템 proxy 주입과 환경 `HTTP_PROXY` 무시,
  Git HTTPS CONNECT]**
- **proxy 인증 정보.** [2026-11-21 사용자 결정](https://github.com/handochan/aelix-studio/issues/32#issuecomment-7056423671)대로
  저장할지는 실행 형태가 정한다. 데스크톱(Electron) 앱은 main process에서 Electron `safeStorage`로 OS keychain
  (macOS Keychain, Windows DPAPI, Linux libsecret·KWallet)에 묶어 암호화한 바이트만
  `proxy-credentials-<id>.json`에 저장한다(`credentialMode: 'keychain'`). `safeStorage`가 암호화를 못 하거나 Linux에서
  OS 비밀 저장소 없이 `basic_text`(또는 `unknown`)로 동작할 때, 그리고 별도 WebUI에서는 저장하지 않는다
  (`'memory-only'`). 그때는 온라인 설치마다 요청으로 인증 정보를 받아 그 변경 동안만 메모리에 둔다. helper는
  Electron을 모른다. host가 암호화·복호화 함수 두 개(또는 memory-only)만 넘기고, 파일은 helper가 `settings.json`과
  같은 방식(변경 잠금, 소유자만 읽는 임시 파일 flush, lock holder의 rename)으로 쓴다.
  - **저장 형태.** `settings.json`에는 인증을 요구하는지(`proxyAuthentication`)와 봉인 파일의 무작위 ID만 둔다.
    봉인 파일은 저장마다 새 ID로 따로 만든다. ID와 proxy 주소는 파일 바깥과 암호문 안에 모두 들어 있고, 연 뒤
    안쪽 값이 맞아야 쓴다. 이름을 바꾸거나 바깥 주소를 고친 파일은 쓰지 않는다. POSIX에서는 그룹·다른 사용자
    권한이 있거나 소유자가 다른 파일도 쓰지 않고 다시 묻는다. keychain이 열지 못할 때도 다시 묻는다.
  - **저장 순서와 복구.** 새 봉인 파일을 먼저 쓰고, 그 ID로 `settings.json`을 바꾼 뒤, 예전 봉인 파일을 지운다.
    중간에 끊겨도 설정은 열리는 파일을 가리킨다. 모든 변경은 잠금을 잡은 직후 설정이 가리키지 않는 봉인 파일을
    지운다. 설정을 읽을 수 없으면 어느 봉인 파일도 건드리지 않는다. 설정이 복구되면 저장된 인증 정보가 다시
    열린다.
  - **지우는 조건.** proxy를 끄거나 주소(scheme·host·port)를 바꾸거나 인증을 끄면 지운다. 주소에 새 인증 정보를
    입력하면 바꾼다. memory-only에서 입력하거나 설치 요청으로 보내면 keychain이 저장해 둔 것도 지운다. 나중에
    keychain이 돌아왔을 때 예전 비밀번호를 다시 쓰지 않게 하려는 것이다. 1b가 저장한 설정은 그대로 읽힌다(인증
    꺼짐).
  - **요청.** 사용자 이름·비밀번호가 든 주소를 입력하면 나눠서 주소만 저장하고 인증을 켠다(함께 보낸
    `proxyAuthentication: false`는 `INVALID_INPUT`). 인증을 요구하는데 저장된 것도 요청에 든 것도 없으면 설치
    도구를 시작하기 전에 `PROXY_CREDENTIALS_REQUIRED`로 답한다. 화면은 이 코드를 받으면 묻는다. 요청에 든 인증
    정보는 저장된 것보다 앞서고 그 설치에만 쓴다. 요청을 확인할 때의 proxy 주소에 묶이므로, 잠금을 잡기 전에 다른
    Studio 프로세스가 주소를 바꿨으면 아무 데도 보내지 않고 `PROXY_CHANGED`로 끝난다. 파일 반입과
    wheel 업데이트는 오프라인이라 인증 정보를 받지 않고, 보내면 `INVALID_INPUT`이다. 온라인 업그레이드에도
    같은 인증 정보 확인, 마스킹, 오류 우선순위가 적용된다.
  - **relay.** 설치 도구는 인증 정보를 받지 않는다. 인증이 필요한 온라인 설치는 잠금 아래에서 마지막 설정 확인
    뒤에 helper 프로세스 안에 그 변경 전용 loopback proxy(relay)를 열고 설치 도구가 끝나면 닫는다. relay는
    127.0.0.1의 임의 port에서 변경마다 새로 만든 무작위 token을 Basic proxy 인증으로 요구한다(상수 시간 비교, 그
    밖에는 407). pip·Git과 pip이 띄우는 빌드 코드는 `http://run:<token>@127.0.0.1:<port>`만 받는다. relay는
    CONNECT 터널과 절대 형식 `http:` 요청을 사용자의 proxy로 넘기면서 `Proxy-Authorization: Basic <user:pass>`를
    붙인다. `https:` proxy에는 TLS로 접속하고 Node와 시스템의 인증서를 믿는다. 인증서 확인(`rejectUnauthorized`,
    host 이름 확인)은 relay가 직접 켜므로 `NODE_TLS_REJECT_UNAUTHORIZED=0`으로도 꺼지지 않는다. 확인에 실패하면
    아무것도 보내지 않는다. 회사 CA를 따로 지정하는 설정은 #99에서 다룬다. port가 없는 주소는 scheme의 기본
    port(80·443)다. 사용자 proxy에는 Basic 인증만 쓴다.
    - **relay 자신의 답.** 로그인에 대한 사용자 proxy의 답은 설치 도구에 넘기지 않는다. 407, 열리지 않은 터널,
      접속 실패, 인증서 확인 실패에는 relay가 직접 `502`와 고정 사유(`Proxy Credentials Rejected`,
      `Proxy Refused Tunnel`, `Proxy Unreachable`, `Proxy Certificate Rejected`)로 답하고, 그 proxy의 헤더와 본문은
      버린다. 407에 답하면 그 연결은 바로 끊어 본문을 더 읽지 않고 자리도 돌려준다. 넘기는 응답에서도
      `Proxy-Authenticate`, `Proxy-Authentication-Info`, `Proxy-Connection`과 hop-by-hop 헤더를 뺀다. 407을 받은
      설치가 실패하면 `PROXY_CREDENTIALS_REJECTED`로 끝나고 저장된 인증 정보는 그대로 둔다. 화면은 이 코드를 받으면
      다시 묻는다. 취소, 시간 초과, 잠금을 잃은 변경은 407을 만났어도 `CANCELLED`·`TIMEOUT`·`CONFLICT`로 끝난다.
    - **제한.** token을 아직 보이지 않은 연결은 동시에 16개까지 받고, 각각 5초 안에 token을 보여야 한다. 사용자
      proxy로의 연결은 동시에 32개까지다(넘으면 `503 Relay Busy`). 접속부터 첫 답까지는 모두 합쳐 30초이고,
      idle만 재는 것이 아니다. 터널이 열린 뒤에는 idle 300초다.
    - **Git credential helper.** Git은 요청이 성공하면 proxy 인증 정보를 credential helper에
      넘기므로(`credential_approve`), Git 설정에 relay 주소의 helper를 비우는 항목을 사용자 항목 뒤에 둔다. 그래서
      비공개 Git의 `credential-store`도 token을 저장하지 않는다.
    - **출력.** token은 주소 밖에도 찍힐 수 있다. 그 변경 동안 token 그대로, 모든 바이트를 `%XX`로 쓴 것, `run:<token>`의
      base64, 사용자 인증 정보의 Basic 값을 설치 도구 출력의 가리기에 문자열로 더한다. relay는 응답·로그·오류에
      인증 정보나 token을 넣지 않는다.
    - **남는 위험.** 설치 중에 도는 코드(빌드 backend 등)는 token을 읽고 그 변경이 끝날 때까지 relay를 쓸 수 있다.
      사용자 비밀번호는 볼 수 없다.
  - **받는 문자.** 사용자 이름과 비밀번호는 출력 가능한 ASCII(0x20–0x7E)만 받는다(2026-11-22 사용자 결정). relay는
    입력한 값으로 Basic 값을 만든다. RFC 7617은 기본 인코딩을 ASCII와 호환된다는 것 말고는 정하지 않고, 선택적인
    `charset` 매개변수의 값으로는 `UTF-8` 하나만 정의한다(2.1절). 그래서 ASCII 밖의 같은 바이트를 proxy 서버마다
    다르게 읽는다. 어디서나 같게 읽히는 범위인 ASCII만 받는다(처음 확인할 때는 번들 pip이 Latin-1로 보내고 그 밖에서
    실패했고, Git은 UTF-8로 보냈다). 사용자 이름에는 `:`를 받지 않는다. Basic 인증이 첫
    `:`에서 나누기 때문이다(RFC 7617 2절). 주소에 입력한 사용자 부분은 보통의 URL 규칙대로 한 번 퍼센트 디코딩한
    뒤 검사하고, 따로 보낸 필드 값은 그대로 받는다. `%41` 같은 값도 그대로다. 주소에 입력할 때(그대로든 퍼센트
    인코딩이든), 저장할 때, 설치 요청에 들어올 때 모두 `INVALID_INPUT`과 같은 고정 문구로 거절하고 값을 되풀이하지
    않는다.
    **[실행: 단위 시험(가짜 keychain과 memory-only, `safeStorage`의 `basic_text`·`unknown`·암호화 없음, 두 중단
    지점, 주소 변경 경합, 읽을 수 없는 설정과 복구, 거절된 인증 정보, 출력의 token), relay 단위 시험(token 없음·다른
    token, CONNECT와 절대 형식, 사용자 proxy의 407·403과 접속 실패, 제한과 기한, TLS proxy와
    `NODE_TLS_REJECT_UNAUTHORIZED=0`), 실제 Git과 번들 pip이 relay를 거쳐 인증을 요구하는 loopback proxy에 정확한
    Basic 값으로 로그인하는 것과 407에 relay의 답만 받는 것, 실제 Git이 믿지 않는 인증서의 https proxy에 아무것도 보내지
    않음, 비공개 Git의 `credential-store`가 token을 쓰지 않음(빈 helper 항목을 빼면 쓰는 것도 확인), 설치 앱
    확인(1a′)에서 실제 lock holder로 봉인 파일 저장과 삭제]**
- **비공개 Git.** [같은 결정](https://github.com/handochan/aelix-studio/issues/32#issuecomment-7011959904)대로 기본
  꺼짐이다. 꺼져 있으면 위의 격리 그대로다. 켜도 이름 설치는 PR #77의 격리 그대로다(로그인할 저장소가 없다).
  git 설치(pip이 git source를 설치할 때와 Studio의 하위 경로 fetch)에만 다음을 더한다. 사용자의 `SSH_AUTH_SOCK`, 사용자 SSH
  설정과 키(`-F /dev/null`과 `IdentityFile=none` 등을 빼고 `BatchMode=yes`·`StrictHostKeyChecking=yes`·
  `UpdateHostKeys=no`는 명령행에 남긴다. 명령행이 설정보다 우선한다), 사용자 Git 설정 중 `credential.*` 항목
  (`/usr/bin:/bin`의 `git`으로 사용자 `HOME`에서 저장소 밖 디렉터리를 기준으로 읽어 하나씩 넘긴다. 다른 Git 설정은
  넘기지 않는다), `GCM_INTERACTIVE=never`, Linux에서는 secret-service helper가 쓰는 `DBUS_SESSION_BUS_ADDRESS`.
  설치 도구의 `HOME`은 계속 후보 전용이라 `~/.netrc`·`~/.gitconfig` 전체·pip 설정은 그대로 제외된다. pip 설정은
  어느 쪽이든 무시한다. OS별로는 macOS가 기본 대상이다(Xcode Git의 `osxkeychain`은 시스템 범위가 아닌
  "unknown" 범위로 보이므로 범위를 지정하지 않고 읽는다). Linux는 `HOME`으로 저장소를 찾는 helper(`store`,
  `cache`를 파일·socket 지정 없이 쓴 경우)가 사용자의 저장소를 찾지 못한다. Windows는 git 설치 자체를 아직
  내지 않으므로 비공개 Git도 적용하지 않는다. 처음 접속하는 SSH host는 터미널에서 한 번 접속해 known-hosts에
  넣어야 한다. **[실행: 단위 시험과 실제 Git 설정 읽기. 실제 SSH agent와 HTTPS credential helper로 비공개 저장소
  설치는 실행하지 않았다]**
- **Git 하위 경로.** [같은 결정](https://github.com/handochan/aelix-studio/issues/32#issuecomment-7011959904)대로
  지원한다. 요청은 URL fragment가 아니라 별도 필드(`subdirectory`)로 받는다. `#subdirectory=` 등 URL fragment는
  여전히 pip 실행 전에 거절한다. 필드는 `/`로 이은 일반 이름만 받는다(`.`·`..`·빈 이름·절대 경로·드라이브·
  역슬래시·`.git`·`-`로 시작하는 이름 거절). 처리는 다음 순서다.
  1. Studio가 git source 설치 도구와 같은 환경으로 저장소를 보관소의 staging 디렉터리(`artifacts/.staging-git-…`)에
     clone하고 revision을 고른다. 전체 object 이름(clone의 object 형식에 맞는 자릿수: SHA-1은 16진수 40자리,
     SHA-256은 64자리. `git rev-parse --show-object-format`으로 읽는다)은 그 object 자체다. SHA-256 저장소의 40자리는
     줄인 이름이라 아래 순서를 따른다. 같은 이름의 branch나
     tag가 다른 commit을 가리킬 수 있으므로 ref로 읽지 않고, clone에 commit으로 있는지 보고 없으면 그 이름으로
     fetch한다. 그 밖에는 pip과 같은 순서다(branch, tag, commit, 없는 `refs/`는 fetch).
  2. 고른 commit을 `git checkout --detach <object>^{commit}`으로 checkout한다. 일반 `git checkout <이름>`은 같은
     이름의 로컬 branch를 먼저 고르는데, 저장소가 기본 branch 이름을 다른 commit의 object 이름으로 지을 수
     있다. 그 뒤 `git rev-parse HEAD`가 고른 commit과 정확히 같아야 하고, 출처에는 이렇게 확인한 commit을 적는다.
  3. 하위 경로에 필요한 submodule만 초기화한다. 요청한 이름을 따라가며 경로 위의 submodule(Git 객체에서
     gitlink인지 본다)을 하나씩, 한 단계씩 초기화하고, 단계마다 그때까지의 경로를 4의 방식으로 확인한 뒤 그
     안으로 들어간다. 하위 경로를 확인한 뒤에는 그 안의 submodule을 모두 초기화한다. 경로 밖의 submodule은
     빌드되지 않으므로 그 주소에는 접속하지 않는다.
  4. 실제 파일 시스템에서 checkout 루트가 경로대로의 실제 디렉터리인지, 경로의 이름마다 `lstat`으로 링크가 아닌
     디렉터리인지, `realpath`가 checkout 실제 루트에 요청한 이름을 이은 경로와 정확히 같은지 본다(대소문자를
     무시하는 파일 시스템의 다른 표기도 거절).
  5. checkout 전체(Git 메타데이터 포함, 저장소에서 버전을 읽는 빌드가 있다)를 새 staging 디렉터리
     (`artifacts/.staging-source-…`)에 복사한다. 복사는 번들 Python이 `openat` 방식으로 한다. 이름마다 부모의
     descriptor를 기준으로 `O_NOFOLLOW`로 열므로, 복사 중에 디렉터리나 파일이 링크로 바뀌면 따라가지 않고
     실패한다. 파일은 `O_NONBLOCK`으로 열고 연 descriptor를 `fstat`해 일반 파일일 때만 읽는다. 목록을 읽은 뒤
     FIFO로 바뀐 이름도 기다리지 않고 거절한다. 링크는 Git이 checkout한 그대로 링크로 복사하고 가리키는 것은
     읽지 않는다. 파일·디렉터리·링크가 아닌 것은 거절한다. Windows에서는 복사를 거절한다(`dir_fd` 열기가 없고
     git 설치도 내지 않는다). clone은 lock holder가 지운다.
  6. 복사본에서 4의 확인을 다시 하고 그 디렉터리를 native에 로컬 경로로 넘긴다. 설치가 끝나면 lock holder가
     복사본을 지운다. 중단으로 남은 staging은 다음 변경의 복구가 지운다.

  확인한 뒤 clone이 바뀌어도 설치되는 것은 확인한 복사본이다. 출처 대조는 그 디렉터리를 기록한 PEP 610
  `dir_info`가 하나인지 보고, 출처 기록에는 저장소 URL, 확인한 commit, 하위 경로를 남긴다. 실패 코드는
  `GIT_FETCH_FAILED`와 `SUBDIRECTORY_INVALID`다. **[실행: 실제 Git과 Python으로 링크 탈출·내부 링크·중간
  링크·파일·없음·대소문자·링크 루트·특수 파일 거절, 목록 뒤 FIFO로 바뀐 이름, commit 이름의 branch, 요청한
  전체 commit 이름의 branch·tag, HEAD 불일치, 중첩 submodule 안의 하위 경로와 필요한 submodule만 초기화, 번들
  native·pip으로 in-tree backend 설치]**

- **Git 전송 정책.** 이름·git 설치 도구와 Studio fetch의 Git에 `protocol.allow=never`,
  `protocol.https.allow=always`, `protocol.ssh.allow=user`(비공개 Git이면 `always`), `protocol.git.allow=user`,
  `protocol.file.allow=user`를 준다. `user`는 사용자가 요청한 저장소에만 허용하고 Git이 submodule 명령에는
  허용하지 않는다. 그래서 저장소가 선언한 submodule은 HTTPS(proxy를 거친다)로만, 비공개 Git이면 SSH로도
  가져온다. `git://`·평문 HTTP·로컬 경로·helper 전송은 submodule에 쓰이지 않는다. pip이 git source를 설치할 때
  초기화하는 submodule에도 같은 정책이 적용된다. **[실행: 실제 Git. SSH submodule은 비공개 Git이 꺼지면 연결 전
  거절, 켜지면 연결. `git://`·`file`은 켜져도 거절. 평문 HTTP는 요청 저장소에도 거절]**
- **출력의 인증 정보.** Git은 원격과 submodule 주소를 저장소에 적힌 그대로 출력하고, 그 주소에 token이 있을
  수 있다. 응답에 넣는 Git·설치 도구 출력에서 주소의 사용자 부분을 `***`로 바꾼다. 허용 문자 목록으로 사용자
  부분의 끝을 정하지 않는다(RFC 3986은 따옴표·괄호 등 sub-delimiter를 허용한다). `scheme://` 뒤 authority는 첫
  `/`·`?`·`#`·공백(또는 다음 `scheme://`, 입력 끝)까지이고, 그 안의 마지막 `@` 앞이 사용자 부분이다. 비밀번호가
  없는 SSH 계정 이름(`ssh://git@host`)만 남긴다. 출력만으로는 주소가 어디서 끝나는지 알 수 없으므로
  애매한 범위는 가린다. 비밀번호에 그대로 든 `"`·`\`에서 authority를 끊지 않고(Git은 설정 값을 풀어 주소를 그대로
  출력한다), 주소 뒤에 공백 없이 이어진 텍스트(JSON의 다음 필드 등)는 함께 가려질 수 있다. 새는 것보다 더 가리는
  쪽을 택했다. 출력의 끝부분만 남기기 전에 먼저 가린다. 자른 뒤에 가리면
  잘린 자리가 주소 안일 때 남은 비밀번호 조각이 주소처럼 보이지 않아 그대로 나갔다. stdout·stderr마다 마지막
  공백 뒤의 내용은 다음 출력이 올 때까지 열어 두어, 여러 조각이나 다른 stream 사이로 나뉜 주소도 통째로
  가린다. 공백 없이 64 KiB를 넘는 덩어리는 조각이 어떻게 나뉘든 표시 하나로 바꾼다. Git의 답(commit, object
  형식, tree 항목)은 stdout과 종료 코드로만 판단하고 stderr의 경고는 보지 않는다. **[실행: 단위 시험. 모든
  sub-delimiter·pct-encoded `@`·따옴표로 감싼 주소·이어 붙은 두 주소와 그 모든 위치의 나누기, 주소 안 모든
  위치에서 자르기, 긴 덩어리의 모든 나누기, 실제 자식 프로세스]**
- 온라인 설치의 접속 대상을 제한하는 수단은 지금 없다. wheel만 받거나 받은 뒤에 검사하는 것은 접속 대상을
  제한하는 것이 아니다. 받는 동안 이미 접속한다. 어떻게 낼지는 사용자 결정이고, 내되 설정으로 끌 수
  있게 하기로 정해졌다(8.2의 A3).
- 이 접속은 [외부 접속 목록](../studio-outbound/README.md)에 "사용자가 명시한 endpoint"와 "사용자가 명시한
  proxy·인증"으로 적었다(Studio #15).

`PROXY_CREDENTIALS_REJECTED`가 더해졌다. 요청·응답 형태의 정본은 `packages/web-host/src/studio-extensions/types.ts`다.

`list`의 상태 이름은 `ready`(준비됨), `manifest_unbound`(manifest 미결합), `reinstall_needed`(다시 설치 필요)다.
관리형 목록으로 검증된 확장에는 `managedId`와 `defaultEnabled`도 포함한다. 출처와 플랫폼이 온라인
업그레이드를 지원하는 항목에 `upgrade`(`available` / `pinned` / `confirmation_required`)가 있다.
화면은 이 값과 `get_settings`의 `onlineInstall`·`onlineInstallLocked`·`unreadable`을 함께 본다.
`ready`는 대화가 받는 형태 그대로 로드 검사를 통과한 pack, 곧 링크 디렉터리로 넘겨 manifest가 결합되는
확장이다(8.3의 B5). 모듈 참조로 넘기는 확장은 코드는 로드되지만 `manifest_unbound`다. 로드 오류 문구에서는
세대·상태 디렉터리·번들·홈 디렉터리 경로를 이름표로 바꾼다. 설치 도구 출력의 끝부분은 그대로다.

### 7.3 ACP에 필요한 것

Studio 쪽에서 우회하지 않고 ACP 변경으로 요청한다.

- **대화의 `/extension install|update|remove`를 명시적으로 막거나 Studio로 넘긴다. 화면 공개(1b)의 선행이다.**
  근거는 다음과 같다.
  - 어댑터는 승인 뒤 worker의 interpreter로 `aelix extension …`을 실행하고, 자신의 환경을 그대로 넘긴다.
    어댑터 자체의 보호는 실행 파일의 실제 경로에 `.app/Contents/`가 있는지 보는 검사 하나다. **[소스]**
  - 권장한 대화 실행 형태에서 환경이 깨끗하면 실패한다. 그러나 어댑터 환경에 `PIP_TARGET`이 있으면 세대에,
    `PIP_BREAK_SYSTEM_PACKAGES`가 있으면 번들 Python에 설치됐다(3.3). 뒤의 것은 번들을 바꾼다. **[실행]**
  - 사용자 pip 설정 파일과 `--extension-manager`도 같은 경계를 바꾼다. **[소스]**
  - Studio가 host와 ACP에 넘기는 환경에서 `PIP_*`·`PYTHON*`·`UV_*`를 빼는 것은 보조 수단이다. host가 ACP를
    띄우는 환경 전체를 Studio가 고정한다고 보장하지 못하고, pip 설정 파일은 환경 변수가 아니다. **[추정]**
  - ACP가 쓰기 동작을 실행하지 않는 것(거부하고 안내하거나 Studio의 설치 절차로 넘기는 것)만이 이 경계를
    닫는다. 대신 ACP와 그 자식의 환경·실행 파일을 고정하는 계약을 둘 수도 있지만, 지금 그런 계약은 없다.
  - launcher 조각의 실행 형태(`launch.py native-generation`)에서 다시 봤다. 깨끗한 환경에서는 install·remove 둘
    다 동의 뒤 `-33002`로 실패하고 세대·포인터·번들은 그대로였다. `PIP_TARGET=<현재 세대 site-packages>`가
    있으면 install이 후보·검증 없이 현재 세대에 그대로 설치됐다. **[실행]**
  - launcher 조각에서는 어댑터 환경의 `PIP_*`를 지우지 않았다. 지우면 에이전트가 사용자 프로젝트에서 쓰는
    pip 설정까지 사라지고, 사용자 `pip.conf`로 같은 경로가 열려 그것만으로는 닫히지도 않는다. 경계는 위의 ACP
    쓰기 차단으로 닫는다. 보조 수단으로 지울지는 1b에서 정한다.
  - 보강 후보(이번 범위가 아니다): helper가 변경을 시작하기 전에 현재 세대의 `RECORD` 해시를 기록과 대조하면
    대화창에서 그 자리에 설치된 것을 잡을 수 있다.
- **모듈 참조의 이름 그림자.** 어댑터는 `--extension`으로 받은 `demo` 같은 맨 모듈 참조를, 대화의 작업
  디렉터리에 같은 이름의 경로가 있으면 세션 시작 자체를 거부한다("A project path shadows this module
  reference"). Studio는 맨 모듈을 `demo:setup`으로 바꿔 넘기고 로드 검사도 그 형태로 한다. native의 `-e`
  로더는 맨 모듈을 그 모듈의 `setup`으로 읽으므로(pin의 `_factory_from_module`) 뜻이 같다. **[소스·실행]**
- **대화의 `/extension list` 문구.** 권장한 실행 형태에서 로드된 확장을 "REFUSED … not loaded"로 적는다(5.2).
- **켜고 끄는 권한.** 기존 `--extension`으로 넘긴 확장은 세션이 끌 수 없다(3.3). ACP #38의 관리형 입력은
  앱 기본값과 대화별 예외를 합친다. 적용 조건은 7.4와 A5를 따른다.
- **설치된 pack을 CLI와 같게 로드하는 정식 방법.** 지금은 모듈 참조와 링크 디렉터리뿐이고 둘 다 entry point
  로드와 다르다(3.3). 설치된 pack을 지정해 entry point와 manifest로 로드하는 인자가 있으면 pack 구조의
  제한이 없어진다. aelix-ai #624의 켜기/끄기 저장이 들어온 뒤 `--no-extensions`를 유지할지도 함께 정한다.

### 7.4 Studio 패키징에서 바꿀 것

- `launch.py`가 세대 `site-packages` 경로를 인자로 받아 `sys.path` 끝에 더한다.
- `launch.py`의 `acp` 모드가 `current.json` 또는 직전 사본에서 번들이 맞는 세대를 골라 lease를 잡는다(5.6).
  세대의 `site-packages`는 native worker의 import 경로에 넘긴다.
- Studio는 관리형 Aelix ACP를 등록할 때 명령별 환경에 `AELIX_STUDIO_EXTENSION_STATE`를 넣는다. 값은 helper와
  같은 절대 경로 `<Studio 사용자 데이터>/aelix-runtime`이다. host는 로그인 셸 환경 다음에 명령별 환경을
  적용하므로 같은 키는 Studio 값이 우선한다.
  `launch.py acp`는 값을 읽고 어댑터 엔트리포인트를 호출하기 전에 환경에서 지운다. 변수가 없으면 번들만으로
  시작한다. [2026-11-20 Issue #32 결정](https://github.com/handochan/aelix-studio/issues/32#issuecomment-7014497017)
- 별도 WebUI는 링크를 해석한 실제 DB 디렉터리로 사용자 데이터를 찾는다. 그 디렉터리가 `<프로필>/aionui`이고
  프로필의 `config`에 `aionui-config.txt` 또는 `.aionui-env` 파일이 있으면 같은 Desktop 프로필을 사용한다.
  그 밖에는 실제 DB 디렉터리 아래에 `aelix-runtime`을 둔다. [Studio PR #79](https://github.com/handochan/aelix-studio/pull/79)
- helper는 `generation.json`의 `launch.managed`에 검증 목록을 적는다. 관리형 입력을 지원하는 ACP에는 lease가
  가리키는 세대 ID, 시작 시 읽은 앱 기본값, 켜짐과 꺼짐을 모두 포함한 목록으로 v1 JSON을 만들어
  `--managed-extensions`로 넘긴다. 모듈이 있으면 같은 세대의 절대 `sitePackages` 경로를 포함한다.
  빈 세대도 빈 목록으로 넘긴다. 스냅샷은 `leases/`에 lease의 보조 파일로 두고 어댑터 종료나 만료 lease 수집 때
  제거한다. 관리형 목록은 스냅샷으로만 넘긴다. 별도 운영자 확장은 ACP 계약의 `--extension`을 따른다.
  [ACP v1 계약](https://github.com/handochan/aelix-acp/blob/a1a32b9afb803ecd1d57c0950882dc907b4bd68f/docs/studio-extension-overrides.md)
- Studio ACP pin `369df4784`는 관리형 v1 입력을 지원한다. 이전 ACP에는 새로 검증한 세대의 켜진 항목을 개별
  `--extension` 인자로 넘긴다. 관리형 검증 이전의 세대는 기존 pack 디렉터리와 모듈 참조를 사용한다.
  대화별 예외는 v1 입력을 지원하는 ACP와 관리형 검증을 마친 세대가 함께 있을 때 적용된다.
- 번들 Python의 자식이 번들에 `.pyc`를 쓰지 않게 한다. PR #45의 launcher 변경이 이것을 한다. 병합 전에는
  helper가 환경 변수를 준다(`NativeAuthService`가 이미 그렇게 한다).
- native wheel, `native-site`, lock, host는 바꾸지 않는다.

## 8. 결정

### 8.1 이 문서의 기술 제안

ADR을 채택하면 함께 확정되는 구현 방식이다.

1. 설치 위치는 사용자 영역의 venv 세대다.
2. 관리는 세대의 venv interpreter로, 대화는 번들 interpreter에 세대를 더해 `-e`로 넘긴 확장을 로드한다(5.2).
3. 설치는 후보 세대에서 하고 5.3·5.5를 통과해야 전환한다. 기대 확장 집합의 대조는 필수다. 잠금·revision·
   lease·복구는 5.6을 따른다.
4. 세대는 번들에 묶는다. 번들이 바뀌면 기존 세대를 고치지 않고 새 후보로 옮긴다(5.8).
5. 설치는 Studio helper 서비스가 하고, 화면 모듈은 5.11의 요청만 쓴다. helper가 띄우는 프로세스의 환경은
   허용 목록으로 만든다(5.4).
6. 확장이 없으면 실행 방식은 지금과 같다.

### 8.2 사용자가 고를 것

사용자에게 보이는 결과가 달라지는 선택만 모았다. 정해야 하는 시점 순서다. 전부를 정해야 1a를 시작하는
것이 아니다. 선택지마다 보이는 결과를 적었고 "권장"은 이 문서의 의견이다. "결정"은 사용자가 2026-11-17
또는 2026-11-19에 고른 선택지와 그 선택지에 적혀 있던 설명이다. 설명에 없던 내용은 결정이 아니다.

**1a(설치 helper)를 시작하기 전**

- **A1. 이 설치 방식을 채택할 것인가.**
  - (가) 채택한다. → 확장은 Studio 사용자 데이터 안의 별도 공간에 설치된다. 앱 번들과 터미널 CLI의 환경은
    바뀌지 않는다. helper 구현을 시작한다.
  - (나) 채택하지 않는다. → #32를 멈추고 다른 방식을 다시 조사한다.
  - 권장: (가).
  - **결정(2026-11-17): (가) 채택.** 설치 helper 구현을 시작한다. 화면에는 아직 내지 않는다. OS별 확인은 그
    다음 단계에서 하고, 화면 공개 전에는 ACP 변경(대화창 설치 차단)이 필요하다. 질문에 함께 적어 보여 준
    제약: Studio에 든 라이브러리와 버전이 충돌하는 확장과 시작 시 자동 실행 파일이 있는 패키지는 설치를
    거부한다. 사용자의 pip 설정은 따르지 않는다(사내 미러는 Studio 설정에 따로 적는다). 파일 반입은 wheel만
    받는다.

**해당 기능을 구현하기 전**

- **A2. 설치한 확장을 대화에서 쓰는 것을 언제 낼 것인가.**
  - (가) 지금 ACP로 낸다. → 설치하면 다음 새 대화부터 확장의 명령과 도구를 쓴다. 확장의 구조에 따라 선언한
    MCP 서버·테마·hook이 빠질 수 있고(3.3), 그런 확장은 화면에 표시한다. 구조가 맞지 않아 로드에 실패하는
    일부 확장은 설치가 거부된다.
  - (나) 필요한 native·ACP 계약과 변경이 된 뒤에 낸다. → entry point·manifest 로드 의미를 맞춘다. 화면 출시가
    그 일정을 기다린다.

B5의 구현(launcher 조각): native `extension verify`가 그 entry point의 manifest가 결합된다고 하고, manifest가
entry 모듈 경로의 패키지에 있고, `[plugin.entry] python`이 entry point 값(맨 모듈이면 `모듈:setup`)과 같고,
plugin id가 다른 pack과 겹치지 않으면 링크 디렉터리로 넘긴다. manifest는 번들 Python의 `tomllib`로 읽기만
한다. 로드 검사는 두 번 한다. 모든 확장을 모듈 참조로 한 번(지연 활성화 pack도 import와 `setup()`을 한다),
pack이 있으면 launcher가 넘길 인자 그대로 한 번. 어댑터가 받지 않을 모듈 참조는 설치를 거부한다.

  확인했고 실제 설치 앱 업데이트로는 확인하지 않았다. 완료 조건의 충족은 helper 구현 뒤에 다시 확인한다.

1a′의 Provider Preview 설치 검증은 설치된 번들의 Python과 ACP launcher를 사용한다. 파일 반입과 loopback
index 설치, 새 ACP 세션의 확장 명령, 잠금 경합과 lease, console script 경로, 되돌리기·제거, 번들 교체 모의의
reinstall_needed를 기록한다. macOS는 ad-hoc 서명을 전후 검증하고, 다섯 target 모두 설치 번들의 파일을
대조한다. Linux 감사에는 이 절차의 하위 프로세스도 포함한다.

Windows 세대의 pack은 junction이고 관리 자식은 Windows Job Object로 묶는다. Windows의 distlib console
launcher는 복사 시 새 interpreter를 가리킨다. 온라인 이름 설치는 격리된 시스템 환경을 쓴다. Windows Git
설치는 시스템 Git·SSH 경로를 확인하기 전까지 보류한다.

## 10. 확인하지 않은 것

- **Windows 기업 정책.** AppLocker처럼 사용자 영역 실행을 막는 정책, 최대 경로 정책을 바꾼 환경,
  시스템 Git·SSH 설치는 OS별 확인에서 별도로 다뤄야 한다.
- **배포 서명과 컴파일된 확장.** Preview macOS 검증은 ad-hoc 서명으로 실행한다. Developer ID·공증 및
  별도로 서명하거나 컴파일한 확장의 ABI·DLL 탐색·library validation은 별도 확인 대상이다.
- **실제 Studio 업데이트.** 번들 디렉터리를 바꿔치기한 모의다.
- **Python minor가 바뀐 번들.** 감지만 했다.
- **링크 디렉터리로 로드한 확장의 선언 기능.** manifest가 결합되는 것까지 봤다. 선언한 MCP 서버·테마·hook의
  동작은 실행하지 않았다.
- **uv로 넘어가는 설치 경로.** 세대에 pip이 있어 대화 실행에서는 pip 경로만 탔다. 번들만으로 실행할 때 uv가
  거부하는 것은 1차에서 봤다.
- **잠금 순서.** 5.6의 포인터 선택·lease 순서는 launcher 조각에서 구현했고, 생성과 잠금 사이에 정리를 끼워
  넣는 harness로 확인했다. 실제 helper와 대화가 동시에 도는 경합의 빈도는 재현하지 않았다. 되돌리기의 순서는
  helper 구현을 따른다.
- **대조를 넣은 뒤의 재구축과 전부 차단한 반입.** 5.5의 요청 대조를 넣은 뒤로는 기록을 다시 설치하는 재구축과
  네트워크를 전부 막은 반입을 다시 실행하지 않았다. 둘은 2차 절차로 실행했다.
- **사용자의 터미널 CLI를 실행하는 목록·설치·제거.** 실행하지 않았다.
- **공개 PyPI에서 확장을 이름으로 설치.** 내부 index(loopback)에서 이름 설치를 했고, 공개 PyPI에서는 확장의
  의존성(`tabulate`)만 받았다.
- **컴파일된 모듈이 든 확장, 의존성이 큰 확장.** 순수 Python 확장으로만 실험했다.
- **외부 접속 감사.** Python 소켓 호출 추적까지 했다. kernel 수준 감사(Studio #15)에는 넣지 않았다.
- **main에서 만든 번들.** 시험한 번들은 #31 branch의 것이다. launcher만 main의 것으로 바꿔 일부를 다시
  실행했다. main의 lock으로 만든 번들 전체로는 실행하지 않았다.

것을 링크를 따라가지 않는 복사본 설치로 닫고, checkout 정리를 lock holder로 옮겼다. submodule은 하위 경로 안의
것만 초기화하고 Git 전송 정책으로 submodule 전송을 HTTPS(비공개 Git이면 SSH도)로 묶었다. Git 출력의 인증 정보를
가린다. 각 지적에 회귀 시험을 더했다.

**2026-11-21, 같은 리뷰어의 재확인(blocking 2, should-fix 2, nit 1).** 요청한 전체 commit 이름을 같은 이름의

복사는 파일을 `O_NONBLOCK`으로 열고 descriptor로 종류를 확인한다. submodule 안의 하위 경로를 다시 지원한다(경로
위 submodule을 한 단계씩). proxy 인증 정보의 후속 결정(`safeStorage`, `basic_text`·별도 WebUI는 매번 묻고
메모리만)을 적었다. commit 이름 문제는 고치기 전에 시험으로 재현했다.

**2026-11-21, 같은 리뷰어의 두 번째 재확인(blocking 1, should-fix 3, nit 1).** 주소의 사용자 부분을 허용 문자

판단한다. 64 KiB 상한을 조각이 나뉘는 방식과 무관하게 적용한다. 요약 표에 경로 위 submodule을 적었다.

**2026-11-22, 같은 리뷰어의 세 번째·네 번째 재확인.** 가리기와 64 KiB 상한을 출력 크기에 선형으로 바꿨다(상한
정규식과 scheme 정규식의 역추적, push마다 버퍼를 다시 훑던 것). authority를 URI에 없는 문자에서도 끊던 변경은
비밀번호에 든 `"`·`\`를 그대로 내보내 되돌렸다. 애매한 범위는 가리고 JSON 등이 함께 가려지는 것은 받아들인다.

**2026-11-22, proxy 인증 정보.** 2026-11-21 사용자 결정(데스크톱은 `safeStorage`, `basic_text`·암호화 없음·별도
WebUI는 저장하지 않고 설치마다 받는다)을 구현해 1b의 거절(`PROXY_CREDENTIALS_UNSUPPORTED`)을 바꿨다. 5.1·5.4·
5.10·5.11에 반영했다. 저장소를 helper에 두고 host는 암호화 함수만 넘기게 한 것은 봉인 파일도 변경 잠금과 lock
holder의 rename·정리를 따라야 해서다. 실행하면서 두 가지를 알게 됐다. 번들 pip은 proxy 인증을 Latin-1로 보내고,
Git은 proxy 주소의 사용자 부분을 두 번 푼다. 받는 문자를 출력 가능한 ASCII로 좁힌 것은 2026-11-22 사용자 결정이다.
같은 이유로 `%`와 16진 두 자리가 든 값도 받지 않는다(5.10).

**2026-11-22, proxy 인증 정보 독립 리뷰(blocking 3, should-fix 4, nit 1).** 설치 도구에 실제 인증 정보를 주던 것을
변경마다 여는 loopback relay로 바꿨다. 비공개 Git의 credential helper가 Git이 넘긴 proxy 인증 정보를 저장했고,
pip이 띄우는 빌드 backend가 환경 변수로 비밀번호를 읽을 수 있었다. 이제 둘 다 relay의 token만 본다. Git에는 relay
주소의 helper를 비우는 항목을 더했다. 요청에 든 인증 정보를 확인 때의 주소에 묶었다(`PROXY_CHANGED`). 다른 프로세스가 그
사이 주소를 바꾸면 새 주소로 보내던 경합이 있었다. 봉인 파일을 저장마다 새 ID의 파일로 만들고, 새 파일 → 설정 →
예전 파일 순서로 바꿨다. 변경 시작마다 설정이 가리키지 않는 파일을 지운다. 봉인 파일은 소유자 전용 권한과 암호문 안의
ID·주소를 확인한다. 함께 보낸 `proxyAuthentication: false`는 거절한다. memory-only에서 입력한 인증 정보는 keychain이
저장해 둔 것을 지운다. 사용자 이름의 `:`는 받지 않는다. 주소의 사용자 부분에 든 비 ASCII는 어느 형태로 들어와도
`INVALID_INPUT`이다. 각 지적은 실제 Git·pip 시험과 고친 것을 되돌리면 실패하는 시험으로 확인했다(`credential-store`
재현 포함).

**2026-11-22, 같은 리뷰어의 재확인(blocking 2, should-fix 3, 결정 1).** 앞의 지적은 모두 풀렸다. relay가
`https:` proxy의 인증서 확인을 직접 켜게 했다. 이전에는 `NODE_TLS_REJECT_UNAUTHORIZED=0`이면 믿지 않는 인증서에도
로그인을 보냈다. 사용자 proxy의 407과 터널 실패를 relay 자신의 `502` 답으로 바꿨다. 이전에는 절대 형식 요청에서 그
proxy의 헤더와 본문이 설치 도구까지 갔다. 407은 `PROXY_CREDENTIALS_REJECTED`로 알린다. 읽을 수 없는 설정에서는 봉인
파일을 지우지 않는다. 출력의 token을 주소 밖에서도 가린다. 기다리는 연결과 사용자 proxy 연결의 수, token 기한,
접속 기한(합계)을 정했다. 결정: `%` 뒤 16진 두 자리 거절을 없앴다. relay가 입력값으로 Basic 값을 만들어 Git의 이중
디코딩이 더는 관계없다. ASCII만 받는 규칙과 사용자 이름의 `:` 거절은 그대로다. 각 지적은 고친 것을 되돌리면 실패하는
시험으로 확인했다.

**2026-11-22, 같은 리뷰어의 두 번째 재확인(should-fix 3, nit 1).** relay가 407에 자신의 502로 답한 뒤에도
사용자 proxy의 끝나지 않는 본문을 계속 읽으며 연결 자리를 잡고 있던 것을 고쳤다. 이제 답하는 즉시 그 연결을 끊는다.
407 뒤의 취소와 시간 초과는 `PROXY_CREDENTIALS_REJECTED`가 아니라 `CANCELLED`·`TIMEOUT`으로 끝난다. hex token에는
`encodeURIComponent`가 아무것도 바꾸지 않으므로, 모든 바이트를 `%XX`로 쓴 형태를 가리기에 더했다. RFC 7617의 문자
집합 설명을 2.1절에 맞게 고쳤다. origin/main(#114·#110)을 merge했다.
